# Полный экспорт ScientificReader

`GET /v1/science/export/{query_id}?snapshot_id=…&manifest_sha256=…` выдаёт
закреплённый именованный результат в NDJSON. Запрос требует действующий READ
доступ и точный SHA-256 файла манифеста. Оператор передаёт клиенту ID снимка,
SHA-256 и имя запроса при подготовке поставки. Существующий
`/v1/science/query/{query_id}` сохраняет просмотр до 500 строк.

## Контракт манифеста

Для полного чтения оператор закрепляет в описании именованного запроса
`export` с `order_by`, `row_count` и одним из двух хешей.

| Поле | Смысл |
|---|---|
| `order_by` | Список имён выходных столбцов. По ним результат сортируется по возрастанию. Составной ключ должен быть уникальным и без NULL. Пустой список с `ordered_sha256` закрепляет полную последовательность именованного SQL. |
| `row_count` | Ожидаемое число строк полного результата. |
| `ordered_sha256` | SHA-256 от результата в оговорённом порядке. Начальные байты — `encoded(columns) + b"\n"`. Затем идут `encoded(row) + b"\n"` для каждой строки. |
| `multiset_sha256` | Проверенный хеш состава строк и их кратностей по формату `full_checksum`. Для него порядок отдельно обосновывается уникальностью ключа. При результате из нуля или одной строки допускается пустой `order_by`. |

`columns` — упорядоченный список пар имени и типа DuckDB, `row` — значения
в том же порядке. `encoded` определён в
`vkm_corpus.api.scientific_snapshot_verification`. Этот формат сохраняет
точность Decimal, двоичные значения и даты. Дубли имён и заданных ключей отклоняются.
Упорядоченный хеш закрепляется из независимо проверенного полного результата.
При пустом `order_by` сервер выдаёт SQL в его исходном порядке, включая
повторные строки. `complete` подтверждает именно закреплённую последовательность.
Определение SQL, поля контракта и роли входов защищены хешем манифеста.

## Проверка выдачи

Клиент принимает `metadata`, затем последовательно читает `row` и ожидает
`complete` в конце. В `complete` находятся фактические `row_count` и
`ordered_sha256`. При опоре на `multiset_sha256` сервер сверяет хеш состава и
возвращает его дополнительным полем. Хеш порядка вычисляется по фактической
последовательности строк. Клиент сверяет счётчик и соответствующие хеши с
полученными строками и закреплённым контрактом. `incomplete` либо отсутствие `complete` означает
незавершённую выдачу даже при HTTP 200. При повторе клиент начинает с первой
строки с теми же ID и SHA. Запрос и последующие порции проходят проверку доступа.

Python читает группы по 128 строк. Предел кодированной строки — 1 МиБ.
Экспорт сканирует проверенные по SHA-256 локальные копии входных таблиц.
Уникальность составного ключа проверяется отдельно от выдачи широких строк.
При совпадении закреплённого ключа с конечным `ORDER BY` без ограничения
строк используется сортировка именованного запроса.
Для закреплённого определения `R3_ports` DuckDB выбирает границы по
`r3_entity_id` и сортирует исходную проекцию порциями до 2 048 строк.
Проверки ключа, доступа, числа строк и хешей действуют на весь экспорт.
Запросу доступны только эти файлы. DuckDB работает с лимитом буфера 256 МБ
и лимитом временных данных 512 МБ в каталоге текущего запроса.
Проверка состава хранит хеши строк и ограничена 300 000 строками на запрос.
Превышение заявленного лимита даёт HTTP 413 до начала передачи.
Это параметры исполнения. Замеры суммарной памяти и времени на реальных
поставках требуют отдельной квалификации. Запросы старых снимков без
`export` доступны через действующий просмотр.
