# Документный pipeline VKM Corpus Platform v0

Владелец — агент C. Код: `src/vkm_corpus/extract/`, `layout/`, `ocr/`, `artifacts/`, `pipeline/`. Решения:
CP-05, CP-08, CP-14, CP-16, CP-22, CP-23 и ответы на ревью H (H-02…H-06, H-11, H-14, H-22…H-24, H-35, H-36, H-50,
H-51) в [журнале координатора](../implementation_work/COORDINATOR_DECISIONS.md).

Pipeline — единственный производитель документного слоя. Он пишет только в STAGING-корень
(`$VKM_DATA_ROOT` с `VKM_DATA_ROLE=producer`, маркер корня `STAGING`). Канонический корень CORE пополняется
публикацией и допуском коммитов (координатор).

## 1. Фазы прогона `vkm-corpus run extract`

| Фаза | Где выполняется | Что делает | Кеш |
|---|---|---|---|
| 1. prepare | subprocess на источник, CPU | реестр → файл, sha256, формат по сигнатуре, число страниц двумя методами, нативное извлечение каждой страницы (`NATIVE_RAW`), класс страницы и маршрут | сводка prep по подписи |
| 2. visual | один subprocess с GPU | рендер 200 dpi, превью 1024 px, доля «чернил», PP-DocLayoutV3 (`LAYOUT_RAW`) | вызов layout по call signature |
| 3. ocr | процесс-оркестратор, asyncio | кропы регионов → GLM-OCR → `OCR_RAW`; сценарий B | вызов OCR по call signature |
| 4. commit | subprocess на источник, CPU | источник целиком пересобирается из кешей, строки контракта, коммит писателем D под lease | журнал коммитов staging |

Падение subprocess не теряет страниц. У источника без результата фазы появляется ошибка `WORKER_CRASHED` или
`TIMEOUT`. Страницы получат строки при следующем коммите из кешей. `--resume` сообщает об источниках, которые
упавший прогон начал, но не закоммитил (H-11). Прогон всегда имеет маркеры START/END и артефакт `RUN_LOG`.

## 2. Форматы и страницы

| Формат | Единица (`page_id`) | Метод счёта | Проверочный метод | Текстовый слой |
|---|---|---|---|---|
| PDF | `p` — физическая страница | PyMuPDF 1.28.2 | pypdfium2 | `PDF_TEXT_LAYER` (NATIVE) или `PDF_EMBEDDED_OCR_LAYER` (EMBEDDED_OCR) |
| DjVu | `p` — `FORM:DJVU` | `djvused -e n` | обход IFF (DJVI — не страницы) | `DJVU_EMBEDDED_OCR_LAYER` (EMBEDDED_OCR) |
| EPUB | `s` — элемент spine | spine через lxml | spine через stdlib | `EPUB_XHTML` |
| DOCX | `r` — страница закреплённого рендера | PyMuPDF по PDF рендера | pypdfium2 по PDF рендера | `DOCX_XML` |

- Расхождение методов не выбирает победителя: документ получает `NEEDS_REVIEW` и ошибку `PAGECOUNT_MISMATCH`.
- Строк страниц всегда ровно столько, сколько даёт основной метод. У упавшей страницы статус `FAILED` и ошибка.
- Координаты объектов — `PAGE_PT_TL`: пункты, начало в левом верхнем углу отображаемой страницы.
  - PyMuPDF отдаёт неповёрнутые координаты относительно CropBox; их умножаем на `rotation_matrix`.
  - DjVu: пиксели с началом внизу слева переводим как `pt = px · 72 / dpi` с переворотом y.
  - EPUB: `bbox_space = NONE`.
- 013 и 022 (CP-05) не открываются. Они получают шаг `INSPECT` со статусом `SKIPPED_BY_REGISTER`, исходом
  `SKIPPED_BY_POLICY` и кодом причины реестра. Статус `UNSUPPORTED` к ним не применяется.
- Ограничения копирования и печати в правах PDF обрабатываются как у обычных файлов (решение пользователя): без
  `UNSUPPORTED`, без кода политики и без флагов. Значение `permissions` остаётся только в сыром `NATIVE_RAW`.

## 3. Классификация и маршрут

Правило `c1`, пороги — в `extract/classify.py`; они входят в хеш конфигурации.

| Маршрут | Страницы | Текст страницы |
|---|---|---|
| `NATIVE` | NATIVE_TEXT, MIXED, VECTOR с текстом | нативный слой. OCR — только регионы формул и таблиц |
| `NATIVE_REPAIR` | слой с CP1251-мохибейком, ремонт прошёл проверку правдоподобия | нативный слой после перекодировки, флаг `ENCODING_REPAIRED` |
| `OCR_OPTIONAL` | скан со встроенным чужим OCR-слоем | слой `EMBEDDED_OCR` (H-02). GLM-OCR — формулы и таблицы, выборка B, источники с решением B |
| `OCR_REQUIRED` | скан без слоя, битый слой, контурные глифы, изображение без текста, DjVu без слоя | GLM-OCR по регионам layout. Без регионов — полностраничный `Text Recognition:` |
| `EMPTY` | нет текста, картинок и путей | пусто. С «чернилами» на рендере страница уходит в OCR |

2-up развороты (037, 243) опознаются по формату страниц источника. Layout выполняется по половинам. Печатных меток у
такой страницы две, логических полустраниц нет (CP-08).

Текст поверх скана — всегда чужой OCR (H-02, проверка E11). На странице `RASTER_SCAN` блоки файлового слоя имеют
origin `EMBEDDED_OCR` и при маршруте `OCR_REQUIRED`, когда слой слишком слаб, чтобы быть основным.

## 4. Layout (PP-DocLayoutV3)

- Модель `PaddlePaddle/PP-DocLayoutV3_safetensors` ревизии `97d101e6…` запускается через transformers 5.x на GPU в
  WSL-venv, офлайн (`HF_HUB_OFFLINE=1`), fp32, батч 1 (около 1.2 GB VRAM, около 70 мс на страницу).
- Сырьё (`LAYOUT_RAW`, KEEP_RAW): все пары «запрос × класс» из top-300 со score ≥ 0.05. Для каждой пары хранятся
  рамки в пикселях рендера и в `PAGE_PT_TL`, а также ранг порядка чтения. Постобработка своя, OpenCV не нужен.
- Регионы (`layout/regions.py`, правило `regions_v1`) и ID детектированных объектов считаются только из сохранённого
  `LAYOUT_RAW`, без GPU (H-03).
- Имена 25 классов восстанавливаются по id, поэтому `display_formula` и `inline_formula` различаются.
- Страница с совпавшей call signature (пиксели рендера, ревизия, веса, конфигурация) повторно в модель не
  отправляется. Путь без модели включается только явной конфигурацией (`use_gpu_layout = False`).

## 5. OCR (GLM-OCR)

- Тонкий клиент `ocr/client.py`: httpx async, семафор, повторы 429/5xx, таймауты. Разрешены только хосты
  `127.0.0.1`, `localhost`, `::1` и `glm-ocr`. SDK `glmocr` не используется; AST-тест проверяет, что его импорта нет.
- Промпты `Text Recognition:`, `Formula Recognition:`, `Table Recognition:`.
- Семплирование: temperature 0, top_p 1e-5, top_k 1, repetition_penalty 1.1, seed 0.
- Потолок ответа по задачам: text 4096, table 6144, formula 1024 токена.
- Кропы — PNG без потерь, в оттенках серого. dpi кропа по задаче:
  - формулы — 300;
  - текст и таблицы — 200, как страницы в SDK GLM-OCR;
  - для сканов dpi не выше собственного разрешения скана и не ниже 150: апсемплинга нет.
- Высокие текстовые и табличные регионы режутся на полосы детерминированно, по пустым строкам пикселей. Высота полосы
  до 1100 px для текста и до 600 px для таблиц (при 200 dpi). Так ограничены длина ответа и память сервера. Таблица
  из полос собирается строками.
- Полоса тоньше 64 px внизу не создаётся: остаток остаётся в последней полосе, и она может превысить предел меньше
  чем на 64 px. Причина — полоски в 3–4 px: процессор изображений модели отклоняет кроп с отношением сторон больше 200.
- Пиксельные хеши кропов страницы запоминаются в манифесте (`OCR_CROPS` в кеше стадий). Коммит находит результаты
  по call signature без повторного рендера; без манифеста кропы рендерятся заново детерминированно.
- Каждая попытка — неизменяемый `OCR_RAW` (content-addressed). В нём хранятся:
  - запрос без пикселей, с хешами изображения;
  - тело HTTP-ответа как есть;
  - `finish_reason` и `usage`;
  - тайминги;
  - модель: id, ревизия, sha256 весов;
  - движок: `/version` и digest образа.
- Индекс попыток — `cache/calls/`:
  `call_signature = sha256(model_id | model_revision | weights_sha256 | prompt | sampling | pixel_sha256)` (H-05).
  Версия движка записывается, но в подпись не входит.
- Нормализация (`ocr/normalize.py`, правило `ocr_normalize_v2`) отделена от сырья:
  - текст — Markdown → текст;
  - формулы — LaTeX без разделителей, номер уравнения;
  - таблицы — HTML → сетка ячеек. Если ответ обрезан потолком токенов, полные строки сохраняются. Хвостовые строки
    без текста отбрасываются: после последней напечатанной строки GLM-OCR иногда зацикливается на пустых `<tr>`.
  Семантика не добавляется.
- Стоп-окно CP-22: последние 200 вызовов. Прогон останавливается, если `finish_reason=length` > 2 %, пустой ответ на
  «чернилах» > 1 % или повторы > 1 %. `--max-model-calls` ограничивает вызовы layout и OCR вместе.
- Флаги вызова (`ocr/quality.py`, правило `ocr_quality_v2`):
  - `TRUNCATED` — `finish_reason=length`;
  - `EMPTY_ON_INK` — пустой ответ на кропе с чернилами;
  - `REPETITION` — зацикленный ответ: одна 6-грамма покрывает не меньше половины токенов, или текст сжимается
    больше чем в 12 раз.
  Повтор измеряется только на распознанном тексте, без HTML-тегов, разделителей `|` и серий одного знака препинания
  (отточия, линейки). Правило v1 считало разметку и помечало любую большую HTML-таблицу. Счётные петли вида
  «N 225, N 226, …» доходят до потолка токенов и ловятся как `TRUNCATED`.
- Флаги — функция сырого ответа. Коммит пересчитывает их текущим правилом, а не берёт записанные при вызове.
  Правило входит в конфигурацию стадии NORMALIZE.
- Сценарий B: выборка около 5 % страниц со встроенным слоем, равномерно по источнику. Метрика — CER слоя против
  GLM (`cer_v1`). Источник целиком переOCR-ивается, если CER > 10 % или доля букв слоя < 0.6, в пределах 4
  GPU-часов. При двух слоях основной выбирается правилом (`is_primary_layer`). CER пишется в
  `pages.native_ocr_cer`, `NEEDS_REVIEW` из-за расхождения слоёв не ставится.

## 6. Артефакты

Хранилище `artifacts/<kind_dir>/<hh>/<hh>/<sha256>.<ext>` — то же правило, что `CanonLayout.blob_relpath`. Blob
пишется один раз. Индекс staging ведётся в `cache/artifacts/`. Строки `artifacts` передаются писателю D вместе с
коммитом источника.

| Вид | Хранение |
|---|---|
| `PAGE_RENDER` 200 dpi | `NOT_STORED_REPRODUCIBLE`: id = sha256 несжатого PPM/PGM, recipe (рендерер, версия, профиль, страница) |
| `PAGE_PREVIEW` | JPEG q85, 1024 px по длинной стороне; визуальный rerank и API |
| `OCR_INPUT`, `OCR_RAW`, `LAYOUT_RAW`, `NATIVE_RAW`, `DOCX_RENDERED_PDF` | KEEP_RAW |
| `FIGURE_CROP` | 200 dpi RGB |
| `TABLE_CROP` | таблица из нескольких полос: входы OCR полос, сложенные по порядку (полосы покрывают кроп без зазоров); у таблицы из одной полосы изображение — сам `OCR_INPUT` |
| `EMBEDDED_IMAGE` | исходный поток XObject; `embedded_image_transcoded` + `original_filter` (H-36) |
| `VECTOR_PATHS_JSON`, `VECTOR_SVG` | пути `get_drawings()` в `PAGE_PT_TL` и SVG страницы (H-24) |

## 7. DOCX (023)

- Рендер: `vkm-corpus run render-docx --source VKM-SRC-023` на хосте с Docker. Образ
  `infra/workstation/libreoffice/Dockerfile`: Ubuntu 24.04, LibreOffice 24.2.7.2, шрифты DejaVu, Liberation и
  OpenSymbol, запуск с `--network none`.
- PDF рендера кешируется как `DOCX_RENDERED_PDF`. Профиль (версия, id образа, хеш списка шрифтов) пишется в
  `pagination_render_profile`.
- Блоки, таблицы, формулы и рисунки берутся из XML. Это объекты документа (`<SID>:doc:…`) с якорем
  `docx_paragraph_path` (H-50). У формулы и рисунка это путь абзаца с номером элемента (`…#math2`, `…#img1`). Тот же
  путь — якорь ID, поэтому проверка B04 пересчитывает ID из строки.
- Страница рендера находится последовательным поиском текста. Это DERIVATION со статусом `RENDER_DEPENDENT`.
- 121 формула OMML хранится сырьём, `normalized_latex` = NULL.
- Рендер даёт 117 страниц; страницы 1–43 совпадают с Phase 1 побайтно. Шрифты VM Phase 1 неизвестны, поэтому
  привязка evidence к страницам 023 остаётся зависимой от рендера.

## 7а. EPUB (249)

- Единица — spine-элемент (`s`). Печатные номера берутся из якорей в порядке приоритета: nav `page-list` → NCX →
  `epub:type="pagebreak"` → `id="page_N"` calibre (флаг `EPUB_PAGE_ANCHOR_CALIBRE`).
- GIF без `alt` — формулы, распознаются `Formula Recognition:` (`EPUB_IMAGE_OCR`). Остальные изображения — рисунки,
  байты сохраняются как есть.
- У блоков EPUB нет рамки, поэтому якорь ID — порядок чтения и текст внутри spine-элемента (правило валидатора B04).
  XPath элемента остаётся в `raw_locator`.

## 8. CLI

```text
vkm-corpus run plan     [--source ID ...|--canary] [--page A-B] [--force] [--failed-only] [--recall-model]
vkm-corpus run extract  [--source ID ...|--canary] [--page A-B] [--resume [RUN]] [--force] [--failed-only]
                        [--plan-only] [--max-model-calls N] [--recall-model --confirm-plan SHA] [--no-ocr]
                        [--concurrency N] [--workers N] [--scan-dpi-max N] [--no-scenario-b]
vkm-corpus run render-docx --source VKM-SRC-023
vkm-corpus run status   [--run RUN]
vkm-corpus ocr check | ocr smoke
```

- **`--force`** имеет один смысл: пересобрать строки и сводки, кеш моделей использовать.
- **`--recall-model`** повторно вызывает модель для закешированной подписи. Он работает только с подтверждённым
  планом: `run plan --recall-model` печатает `plan_sha256`, затем `run extract --recall-model --confirm-plan <sha>`.
  Если план изменился, прогон отказывается.
- **Повторный прогон** без изменений: источник `UP_TO_DATE`, 0 вызовов модели, 0 новых коммитов. Коммит с тем же
  содержимым — no-op писателя D.

## 9. Ограничения v0

- Библиография (`bibliography_entries`) пока пустая. Сегментация — следующая задача; в EPUB записи `BIBe-*`
  типизированы как `REFERENCE_LIST`.
- Тип рисунка всегда `UNKNOWN_FIGURE_TYPE`. Класс layout (`CHART`) пишется в `layout_class`.
- Подписи рисунков и таблиц связываются по геометрии (DERIVATION, флаги `CAPTION_*`). Для DOCX и EPUB связи нет.
- Планы шахтных полей с регулярной сеткой панелей PP-DocLayoutV3 иногда размечает как `table`. Пример — 014, стр.
  103–105, рис. 3.18–3.20. Тогда запускается OCR таблицы, и ответ выходит галлюцинацией. Такой ответ несёт флаги
  `TRUNCATED` или `REPETITION`, а план остаётся изображением таблицы. Содержимое, повёрнутое на 90° внутри страницы
  (альбомные карты и таблицы), перед OCR не разворачивается.
- На WORKSTATION VRAM делят vLLM и рабочий стол Windows. При переполнении WDDM выгружает память vLLM в системную, и
  генерация падает на порядки. Параметры сервера — у координатора; клиент ограничивает конкурентность.
