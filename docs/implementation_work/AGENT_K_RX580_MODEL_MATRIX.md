# AGENT K — RX580: матрица моделей (§26)

Дата: 28.09.2026. CORE, AMD RX 580 8 GiB (gfx803), Vulkan/RADV Mesa 25.0.7, llama.cpp b11223 + патчи 0001/0002
([BACKEND_RESEARCH](AGENT_K_RX580_BACKEND_RESEARCH.md)). Parity-методика — [PARITY_RESULTS](AGENT_K_RX580_PARITY_RESULTS.md).
Сырые результаты — `/srv/vkm-rx580/bench/results/model_<key>_<quant>[_<variant>].json` на CORE (runtime-данные);
таблица строится `python -m vkm_corpus.embeddings.summarize <results>`.

## 1. Как измерено

Один прогон = одна модель × один квант, `llama-server` с `-ngl 999 -c 4096 -b/-ub 2048 -np 4 -t 4 -fa auto`,
Vulkan-буферы только в device-local VRAM (`GGML_VK_DISABLE_HOST_VISIBLE_VIDMEM=1`, см. BACKEND_RESEARCH §2.1):

1. загрузка и прогрев (4 запроса) → **VRAM процесса** (DRM fdinfo `drm-memory-vram`, после прогрева);
2. **parity**: 60 запросов + 1918 документов пробы по тем же token ids, что у эталона (HF fp32), → gate;
3. **латентность запроса**: 60 запросов × 3 повтора последовательно, по одному (клиент → HTTP → JSON → постобработка),
   p50/p95;
4. **пропускная способность документов**: первые 512 документов пробы (блоки), пакеты по 8, 2 клиента → docs/s,
   tokens/s, средняя загрузка GPU;
5. латентность после простоя 8 с (runtime PM; без keepalive).

Колонки §26: Model / Backend / Precision / Load / VRAM / Embed works? / Parity / Latency / Concurrent-capable / Notes.
«Concurrent-capable» = модель работает как отдельный процесс рядом с другой резидентной моделью (пары — в
[CONCURRENCY_RESULTS](AGENT_K_RX580_CONCURRENCY_RESULTS.md)); все модели ниже — отдельные процессы без общих
блокировок, поэтому concurrent-capable по построению; фактическая совместная работа проверена парами.

Условия, влияющие на сравнение (записаны в каждом результате): бинарник — dev-сборка `llama-vk` того же дерева
(0001–0003; 0004 проверен отдельно, BACKEND_RESEARCH §4); прогоны с 04:00 UTC — с `--cache-ram 0` (§5); numpy
харнеса — с OpenBLAS с 03:23 UTC (до этого — эталонный BLAS: late-модели того периода — BGE-M3 Q6_K/Q5_K_M —
перезапущены, у dense-моделей numpy делает только нормализацию).

## 4. Наблюдения

1. **Все 14 кандидатов работают на RX580** через Vulkan: XLM-RoBERTa (BGE-M3), XLM-RoBERTa+rotary
   (jina-colbert-v2 128/64), ModernBERT (granite r2, mDenseOn, mLateOn), EuroBERT (jina-v5-nano), Qwen3 causal
   (Qwen3-Embedding, jina-v5-small) и bidirectional (pplx dense/context/late, Giga). Нужные доработки — конвертер
   (патч 0001) и память Qwen3 (0002); операторов, которых нет в Vulkan-бэкенде, не встретилось.
2. **Q8_0 — рабочая точность RX580.** Все dense- и ColBERT-выходы проходят gate с запасом (doc cos mean ≥ 0,9986,
   top-10 0,97–0,99, Spearman ≥ 0,994); исключение — multi-vector BGE-M3 по токенному критерию (PARITY_RESULTS §2.1).
   Q6_K проходит у большинства с меньшим запасом, но **падает у pplx-embed-0.6b и Giga-480M** (cos mean 0,994–0,995:
   выход без нормализации / int8 чувствительнее). Q5_K_M проваливает gate у granite-97m (скрытый размер 384 не кратен
   256 → запасные типы), mDenseOn, mLateOn, Qwen3-Emb и BGE-M3; проходит у granite-311m и jina-v5.
3. **F16 на Polaris невыгоден:** точность идеальная (cos 1,0), но у GCN4 нет fp16-арифметики — пропускная способность
   документов в 2–2,6 раза ниже Q8_0, латентность запроса у Qwen3-класса ×5 (138 против 28 мс).
4. **VRAM не ограничение:** малые энкодеры 100–220 MiB на процесс, BGE-M3 и jina-colbert ≈ 390 MiB, Giga ≈ 610 MiB,
   pplx ≈ 740 MiB, causal Qwen3 1,0–1,2 GiB (из них 448 MiB — KV-кеш при ctx 4096; патч 0002 убрал ≈ 1,2 GiB
   логитов из compute-буфера). В 8 GiB помещаются пары и даже тройки моделей.
5. **Скорость:** granite-97m ≈ 233 док/с и p50 6 мс; ModernBERT/EuroBERT ≈ 77–88 док/с, p50 10–12 мс; BGE-M3 и
   jina-colbert ≈ 29 док/с, p50 28–32 мс; pplx ≈ 21 док/с; causal Qwen3 ≈ 15 док/с, p50 28 мс. GPU загружен на
   93–99 %: узкое место — GPU. (Ранняя оценка «BGE-M3 — 57 % GPU из-за голов в numpy» оказалась артефактом эталонного
   BLAS в контейнере харнеса; с OpenBLAS головы 1024×1024 занимают миллисекунды.)
6. **Холодный старт после простоя** (runtime PM, без keepalive): ≈ 930–950 мс на первый запрос — против 18–35 мс в
   тёплом состоянии; сервис держит keepalive 2 с (CP-31).
7. **Память хоста важнее VRAM** (BACKEND_RESEARCH §2.1b): без `--cache-ram 0` у causal Qwen3 RSS процесса 8,4–8,5 GiB
   (prompt cache сервера); буфер логитов добавлял 1,0–2,1 GiB закреплённой памяти (GTT) на процесс — устранён
   патчем 0004 (§5).

## 5. Память хоста и патч 0004

Колонка «VRAM» выше — только часть расхода. В конце каждого прогона матрицы (0001–0003, до 04:00 UTC без
`--cache-ram 0`) процесс `llama-server` занимал на хосте:

| Класс моделей | RSS, MiB | GTT (закреплённая системная память), MiB | Причина |
|---|---|---|---|
| causal Qwen3 (Qwen3-Emb, jina-v5-small) | 8410–8516 | 1334–1511 | prompt cache сервера (KV простаивающих слотов, до 8 GiB) + буфер логитов |
| прочие (BERT/ModernBERT/EuroBERT, bidirectional Qwen3) | 230–650 | 1044–2158 | буфер логитов n_vocab × n_outputs (словари 128k–262k) |

С `--cache-ram 0` у Qwen3-Emb RSS 302 MiB (canary-прогон того же GGUF). Патч 0004 убирает буфер логитов: A/B на
4 моделях — выходы побитно равны, GTT 823 → 34 MiB (granite-311m), 819 → 34 (mLateOn), 710 → 183 (Qwen3-Emb),
713 → 187 (pplx) — BACKEND_RESEARCH §2.1b. Production-образ и сервис содержат оба исправления: пара малых энкодеров
занимает на хосте ≈ 0,8 GiB RSS и < 0,1 GiB GTT.
