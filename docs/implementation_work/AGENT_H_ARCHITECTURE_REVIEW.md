#### H-02 · BLOCKER · F · встроенный чужой OCR-слой помечается как NATIVE

- **Доказательство.** 6 591 страница из 25 975 (25,4 %): 4 934 PDF класса `RASTER_SCAN|TEXT` и 1 657 DjVu со слоем
  `TXTz` (сырьё C: `summary.json` — `EMBEDDED_TEXT_LAYER: 6591`; `budget.json`; C стр. 26, 303). C называет это
  `EMBEDDED_OCR_LAYER` неизвестного движка, «а не нативный текст» (C стр. 341–342, 690, 810). В D: `origin = NATIVE`
  включает «текстовый слой DjVu» и текстовый слой PDF (D стр. 718); `text_layer ∈ {PDF_TEXT_LAYER, DJVU_TEXT_LAYER,…}`
  (стр. 834); `pages.origin = NATIVE` для PDF/DjVu (стр. 413); `primary_text_origin ∈ {NATIVE, OCR, NONE}` (стр. 436).
  E и G наследуют. Качество таких слоёв плохое: систематические подмены букв в слое 230 (C стр. 341); в quote-check
  Phase 1 — `OCR_TEXT_MISMATCH` 1 025 и `VISUAL_NOT_IN_TEXT_LAYER` 1 111 записей (A стр. 446).
- **Риск.** На вопрос §50 «native или OCR?» четверть корпуса отвечает неверно. Агент принимает чужой нераспознанный
  OCR за «собственный текст файла» — это подмена §49 «OCR → FACT» через метку. `origin` входит в хеш ID (D стр. 1039,
  1054): исправление после full run сменит все ID этих страниц. Будущий crosswalk evidence (`extraction_method =
  TEXT_LAYER` у Phase 1) приравняет такой текст к нативному.
- **Рекомендация.**
  - `origin` += `EMBEDDED_OCR` (или `OCR` + `model_id = UNKNOWN_EMBEDDED_ENGINE`, решение координатора);
    `text_layer` += `PDF_EMBEDDED_OCR_LAYER`, `DJVU_EMBEDDED_OCR_LAYER`; `primary_text_origin` += `EMBEDDED_OCR`.
  - Поля `embedded_layer_evidence` ∈ {HIDDEN_TEXT_LAYER, VISIBLE_OVER_IMAGE, DJVU_TXT} и `text_layer_producer`
    (Producer/Creator PDF, как предлагал C стр. 811–812). Текстовый слой DjVu — по умолчанию `EMBEDDED_OCR`.
  - Статус страницы: запрет `NATIVE_OK` при `primary_text_origin = EMBEDDED_OCR`; ввести `EMBEDDED_TEXT_OK` (расширение
    минимума §44) — решение координатора.
  - Валидатор: страница класса `RASTER_SCAN` ⇒ `origin ≠ NATIVE`. E `origin` и G `extraction_mode` — тем же словарём.
- **Кому.** D, C; E, G.

#### H-03 · BLOCKER · C · layout-модель вне конверта, нет `LAYOUT_RAW`

- **Доказательство.** C прогоняет PP-DocLayoutV3 на **всех** страницах как «единый генератор предложений регионов» и
  хранит сырые детекции в `artifacts/layout_raw/` (C стр. 751–755, 937). В D нет вида артефакта для layout
  (`ArtifactKind`, D стр. 847–852; каталоги `kind_dir`, стр. 1146–1147). `model_id/model_revision` — «✓ при OCR» (D
  стр. 700; D02 стр. 1878): рисунок или формула на нативной странице получает `origin = NATIVE`, `model_id = NULL`, хотя
  регион породила нейросеть. `producer_key` несёт одну пару модели (стр. 1022–1023). D просит C подтвердить
  детерминизм детекторов (стр. 2000) — C не подтверждает. Сырой OCR ссылается на layout (`layout_ref.artifact_id`, C
  стр. 921). Запасной путь без GPU даёт другой набор регионов (C стр. 757–759).
- **Риск.** (1) §50 «кто создал / revision модели» неверен для всех детектированных объектов. (2) Канон нельзя
  пересобрать из raw + raw OCR без GPU: без сохранённых детекций layout перезапускается, bbox меняются (недетерминизм
  GPU, версия transformers) → меняются ID (якорь bbox с шагом 0,1 pt, D стр. 1029–1030) и кропы → промах кеша OCR →
  повторный OCR. (3) Ссылки `layout_ref` висят.
- **Рекомендация.**
  - `ArtifactKind.LAYOUT_RAW` (`KEEP_RAW`, публикуется на CORE вместе с `OCR_RAW`).
  - В конверт: `region_origin` ∈ {PDF_XOBJECT, VECTOR_CLUSTER, LAYOUT_MODEL, EPUB_ELEMENT, DOCX_ELEMENT, OCR_MODEL} и
    `models: list<struct<role, model_id, model_revision>>` с ролями LAYOUT и RECOGNITION.
  - bbox и ID детектированных объектов вычисляются **только** из сохранённого `LAYOUT_RAW`; стадия layout не
    перезапускается при совпадении подписи.
  - Путь без GPU — только явной конфигурацией (иной `extractor_id`), не автоматически.
  - Валидатор: `region_origin = LAYOUT_MODEL` ⇒ есть модель с ролью LAYOUT.
- **Кому.** D, C.

#### H-05 · BLOCKER · C · подписи, кеш модели и `--force`

- **Доказательство.** C: одна подпись стадии, включающая `pipeline_version`; версия бэкенда в подпись не входит (C стр.
  955–965); кеш — журнал `$VKM_DATA_ROOT/ledger/` (стр. 968); `--force` = «новые сырые файлы, старые остаются» (стр. 977),
  но имя сырого файла — хеш канонического запроса (стр. 909–911), так что повтор того же запроса даёт то же имя. D:
  `stage_signature` + `call_signature` с `backend_version` (D стр. 1411–1420); `--force` пересчитывает строки и
  переиспользует кеш вызовов (стр. 1427); раскладка сырья content-addressed (стр. 1144–1147); кеш ключуется байтами PNG.
- **Риск.** По схеме C подъём `pipeline_version` повторно OCR-ит ≥ 3 406 страниц; по схеме D обновление vLLM молча
  запускает переOCR. Сырьё перезаписывается или теряется. MCP-параметр `force` (G стр. 533) имеет два смысла. Смена
  Pillow/zlib меняет байты PNG при тех же пикселях → промах кеша.
- **Рекомендация (DN-D-05).** Две подписи D.
  - `call_signature = sha256(model_id | model_revision | weights_sha256 | prompt | sampling | input_pixel_sha256)`, где
    `input_pixel_sha256` — хеш декодированного буфера пикселей с размером и режимом. `backend`/`backend_version`
    пишутся, в подпись не входят; строгий режим — явный флаг.
  - Сырой OCR — content-addressed blob + строка индекса с `call_signature` и `attempt`; повтор при недетерминизме —
    новая попытка, прежняя остаётся.
  - Один смысл `--force`: пересчитать строки, кеш модели использовать. Повторный вызов модели — отдельный флаг, только
    через `--plan-only` и подтверждение.
  - Журнал C не нужен: ledger = `processing_steps`.
- **Кому.** Координатор, C, D; G (семантика `force` в MCP).

#### H-08 · MAJOR · R · head по часам и блокировка через PG

- **Доказательство.** Head источника = последний маркер по `committed_at`, затем `commit_id` (D стр. 1355–1357);
  «Блокировку на уровне задания даёт control plane» (стр. 1451); `parent_commit_id` в маркере уже есть (стр. 1246).
- **Риск.** Полный прогон, начатый раньше, но закоммитивший позже, вытесняет свежий точечный reprocess (или наоборот).
  Часы WSL сдвигаются после сна хоста. Корректность канона зависит от PG, хотя PG по постановке можно потерять (§16,
  §46).
- **Рекомендация.** Оптимистическая конкуренция: коммит допускается, только если его `parent_commit_id` равен текущему
  head источника; иначе `CONFLICT` без автоматического разрешения (нужен новый прогон от актуального head). Время в
  порядке не участвует, `committed_at` — справочно. Для параллельных CLI-прогонов на одной машине — lease-файл
  источника в staging.
- **Кому.** D, координатор.

#### H-09 · MAJOR · C · допуск коммитов на CORE

- **Доказательство.** Публикация — rsync неизменяемых файлов, маркеры последними, снимок только на CORE (D стр.
  1452–1456; CP-15). Существование blob-ов артефактов валидатор проверяет выборкой, полностью — только в `--deep` (F10,
  D стр. 1903). Блокирующий FAIL останавливает весь снимок (стр. 1303, 1852). Кто запускает снимок и пересборку
  проекций на CORE, не описано. На CORE сервисы — в Docker без uv (CP-20 D9), версия кода валидатора может отставать от
  producer (A02 требует «известной коду схемы», D стр. 1858). `gc --orphans` (стр. 1365) может удалить файлы
  незавершённой публикации.
- **Риск.** Снимок с отсутствующими blob-ами проходит валидацию, API отвечает 404/409. Один дефектный источник
  блокирует публикацию всего прогона. Взаимоблокировка «новая схема на WORKSTATION — старый образ на CORE». Скрытая
  зависимость worker → SSH → CORE.
- **Рекомендация.**
  - `vkm-corpus core admit` по коммитам: sha всех файлов партиций; существование и sha всех **новых** blob-ов
    (полностью: новых мало); схема известна коду CORE; проверка родителя (H-08). Допущенные коммиты идут в снимок,
    отклонённые — в `rejected_commits` с причиной и не блокируют остальные. Глобальные проверки (F01 и др.) остаются
    блокирующими.
  - `vkm-corpus core reconcile` = admit → snapshot → validate → `CURRENT` → DuckDB → Neo4j → OpenSearch; одна точка
    входа, запускает оператор или worker через SSH.
  - rsync без `--inplace`, затем `sync`; маркеры последними. GC сирот — только старше lease (например, 24 ч).
  - Гейт кода: схемы producer известны образу CORE, иначе admit отказывает понятной ошибкой.
- **Кому.** Координатор, D, E.

#### H-11 · MAJOR · C · журналы прогона без коммита невидимы

#### H-12 · MAJOR · до MCP write · план reprocess разорван между API и worker

- **Доказательство.** План и `confirmation_token` считает API на CORE по DuckDB и подписи (G стр. 583–589); исполняет

- **Рекомендация.** Единственный планировщик — worker. API ставит `PLAN_REQUEST`; worker публикует план в PG

## 4. Оценка CP-15 и других решений

### 4.1 CP-15 «producer/publisher»

**Принять с десятью обязательными изменениями.** Верно: единственный писатель снимков на CORE, проекции только из
`CURRENT`, потеря PG не теряет корпус, всё невоспроизводимо-дорогое публикуется на CORE. Не хватает:

1. Разделения корней `STAGING` / `CANONICAL` (H-07).
2. Допуска по коммитам и одной команды `reconcile` на CORE (H-09).
3. Head источника по цепочке `parent_commit_id`, без часов (H-08).
4. Публикации всего, что нужно для пересборки без GPU: `OCR_RAW`, `LAYOUT_RAW`, конфиги прогонов, логи прогонов; для
   `NATIVE_RAW` и рендеров — `materialization` + `recipe` (H-03, H-11, H-23).
5. Гейта версии кода CORE относительно producer (H-09).
6. Worker — единственный планировщик; статусы задания до `ADMITTED` (H-12).
7. PG — только операционное состояние; корректность канона от PG не зависит; отдельная БД и роль (H-08, H-42).
8. Обратной копии канона и `KEEP_RAW` на WORKSTATION и `pull-index` (H-10).
9. Одной compose-сети CORE, образов по digest, API/MCP в Docker с `:ro` (H-26). Скрипт уже развёрнутых Neo4j 5.26.31 и
   OpenSearch 3.8.0 закрепляет теги, а не digest; привязку к loopback и выключенный security plugin проверить в canary
   (К-24).
10. Время (`committed_at`, `created_at`) не используется для порядка и выбора; фиксировать `clock_source` хоста.
