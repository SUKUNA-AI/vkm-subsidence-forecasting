## 3. Формат хранилища токен-векторов (pack)

Parquet-части остаются каноническим хранилищем; pack — пересобираемая проекция их текущих строк для единиц одного
снимка (`vkm.multivector_pack/1`):

```
<late config dir>/packs/<pack-id>/
    tokens.f16      float16 [токенов, 128], row-major, little-endian, без заголовка (np.memmap)
    index.parquet   строка на единицу в порядке pack'а: unit_id, kind, page_id, source_id, object_ids, text_hash,
                    token_offset (int64), n_tokens (int32)
    pack.json       манифест (пишется последним): конфигурация и её подпись, снимок, units_sha256, счётчики,
                    размеры и sha256 файлов, sha256 манифестов артефакта, отчёт §64, время
<late config dir>/packs/CURRENT   указатель {"pack_id", …}; атомарная замена после проверенной сборки (--publish)
```

- Порядок: единицы одной страницы подряд (page_id, затем unit_id) — MaxSim страницы читает один непрерывный отрезок.
- `pack-id = <snapshot>-<sha256(подпись, unit, text_hash, часть, строка …)>[:12]`: та же выборка — тот же pack
  (повтор — `EXISTS`). Хранится ≤ `--keep` pack'ов; тот, на который указывает CURRENT, не удаляется никогда.
- Проверки §64 до записи: суммы частей, одна подпись (и model id/revision), ожидаемые единицы = единицы снимка, нет
  дублей (unit, text_hash), нет пропусков, подпись строки, token_count > 0, размерность, конечность, L2-норма
  каждого токена. Провал — pack не пишется, CURRENT не двигается.
- float16 — MODEL_CHOICE пути обслуживания (вдвое меньше байт); отклонение MaxSim измеряет `embed pack-verify`
  (на тестовых данных < 0,5 % относительного; для корпуса — шаг 2 runbook'а).
- Сервис: `PackStore` держит в памяти только индекс (id, страницы, объекты, смещения); токены — `np.memmap`, ОС
  подгружает затронутые запросом страницы. После каждых `multivector_rss_budget_mib` (256) прочитанных МиБ
  отображение сбрасывается `madvise(MADV_DONTNEED)` — страницы остаются в page cache, RSS процесса ограничен
  (синтетика: RssFile 57 МБ при pack'е 1,5 ГБ). `PackHandle` перечитывает `packs/CURRENT` не чаще раза в
  `multivector_check_s` (10 с) и подменяет pack без перезапуска (запросы в полёте дорабатывают на старом); pack чужой
  модели (веса, квантизация, токенизатор, голова, размерность ≠ late-кодировщику запроса) — отказ (`MISMATCH`).
- `InMemoryMultiVectorStore` оставлен для тестов и малых наборов (умеет те же цели при переданных метаданных единиц).

## 4. Поздняя стадия гибридного поиска (контракт)

- Запрос: `late: bool | null` (null — умолчание сервера), `late_candidates` 1…200 (по умолчанию 100 — схема J
  «RRF(BM25, dense) top-100 → mLateOn»). Поля есть у POST/GET `/v1/search/hybrid`, MCP `search_hybrid` и
  `retrieval_trace`, CLI `search hybrid` / `hybrid-smoke`.
- API → RX580 `POST /search/late` с `targets = [{"id", "kind"}]` первых N ключей RRF. Страница (PAGE) получает
  max MaxSim по единицам страницы, кроме BIB_ENTRY (CP-42, ниже); FIGURE/TABLE/FORMULA — MaxSim своей единицы (одна
  единица = один объект).
- Порядок: разные виды не сравнивают сырые оценки (H-44) — каждый вид сохраняет позиции, которые ему дал RRF, и
  внутри них переупорядочивается по MaxSim; при одном виде это просто порядок по MaxSim. Кандидаты без
  токен-векторов идут после оценённых своего вида в порядке RRF и перечислены (`late_status = NO_TOKENS`,
  `stages.late.unscored_ids`); ключи за пределами N сохраняют порядок RRF (`NOT_CANDIDATE`).
- Трасса хита: `late_rank` (внутри вида), `late_score`, `late_status`, `late_unit` (лучшая единица, число единиц и
  токенов), `final_rank`; `fused_rank`, `rrf_score` и ранги BM25/dense сохраняются. `stages.late`: модель, подпись
  запроса, число токенов запроса, pack (id, снимок, подпись, размеры), кандидаты / оценено / без токенов, время.
  Предупреждение `LATE_STORE_SNAPSHOT_MISMATCH`, если pack и векторный индекс построены из разных снимков.
- Решение координатора CP-42: единицы BIB_ENTRY не участвуют в ранжировании страниц — список литературы не тема
  страницы. PAGE-нога dense k-NN исключает `unit_kind BIB_ENTRY` (`must_not`), поздняя стадия оценивает страницу по
  остальным её единицам (`/search/late`: `page_exclude_kinds`, по умолчанию `["BIB_ENTRY"]`; API передаёт явно).
  Единицы BIB_ENTRY кодируются, индексируются и остаются доступными как явные цели `BIB_ENTRY` (будущий поиск по
  библиографии).
- Отказы громкие: нет late-модели (404), нет хранилища, нет опубликованного pack'а, pack чужой модели (503),
  сервис недоступен — `DEPENDENCY_UNAVAILABLE` (стадия `hybrid_late`); 401/403, ответ старого контракта или ответ не
  по тем целям — `DEPENDENCY_ERROR`; тайм-аут — `DEPENDENCY_TIMEOUT`. Подмены «RRF без late» нет.

### 9.1 Детектор библиографических запросов

`src/vkm_corpus/search/intent.py`, правила без модели (MODEL_CHOICE). Запрос библиографический, если есть хотя бы

### 9.2 Маршрут

Для запроса, который детектор пометил (или при `bib_route=true`), выполняются три шага.
1. Сервис RX580 сканирует late MaxSim все записи BIB_ENTRY (`/search/late` с `scan_kind`).
2. Страницы упорядочиваются по лучшей своей записи. Фильтры и дубли страниц применяются через индекс страниц. Этот
   список становится третьей ногой RRF для кандидатов PAGE.
3. Поздняя стадия оценивает эти страницы по всем их единицам, включая BIB_ENTRY.

Для всех остальных запросов действует CP-42. Маршруту нужна поздняя стадия: при `late=false` статус
`SKIPPED_LATE_OFF`, выдача прежняя.

В API и MCP:
- поле `bib_route`: null — решает детектор, true — включить, false — выключить;
- в записи результата — `route`;
- в трассе — `bib_rank`, `bib_score`, `bib_unit`;
- в `stages.bib_route` — статус (APPLIED, NOT_DETECTED, OFF, SKIPPED_NO_PAGE_KIND, SKIPPED_LATE_OFF), признаки, число
  просмотренных записей, время.

Отказы сканирования громкие (стадия `bib_scan`).

Оценка — на стенде V1 (снимок `…5d669f09`, правила библиографии v2). E, пересчитанная скриптом, совпадает с E из V1:
максимальная разница nDCG@10 — 5·10⁻⁵. Метрика — nDCG@10. V — VERIFIED, P — VERIFIED + пул.

| Вариант (7 библиографических запросов) | P: Δ к E [95 % ДИ] | p | победы/поражения | V: Δ | p |
|---|---|---|---|---|---|
| **выбран**: BIB — третья нога RRF, late по всем единицам страницы | **+0,195** [0,122; 0,273] (0,597 → 0,792) | 0,016 | 7/0 | +0,154 [−0,011; 0,313] (0,082 → 0,236) | 0,16 |
| только late по всем единицам страницы (без новых кандидатов) | +0,201 | 0,016 | 7/0 | +0,070 | 0,31 |
| только нога RRF, late с CP-42 | +0,147 | 0,09 | 5/2 | +0,043 | 0,75 |
| нога RRF + late с CP-42 | −0,014 | 0,13 | 0/4 | 0 | 1 |

- Recall@50 выбранного варианта: P +0,399 (p = 0,016), V +0,700 (p = 0,03). judged@10 на P — 1,0.
- Остальные запросы: у 137 текстовых и 42 визуальных Δ nDCG@10 = 0 на V и на P (0 побед, 0 поражений). Из них
  детектор сработал на одном (T-ENT-006, DOI), его nDCG@10 не изменился.
- Почему не «только late»:
  - Приближение после обновления dense до итогового снимка — dense-единицы, оставшиеся в снимке.
  - В этом приближении выигрыш «только late» падает до +0,145, у выбранного варианта остаётся +0,194 (7/0).
  - Выбранный вариант сам приводит страницы списков литературы в кандидаты, а «только late» зависит от того, попали
    ли они в top-100 E.
- Почему только по детектору: если применять выбранный вариант ко всем запросам, на 137 прочих P теряет 0,005
  nDCG@10 (p = 0,19) и 0,026 Recall@50 (p = 0,0001). У варианта «только нога RRF» потеря была бы 0,468.

### 9.3 Хранилище: записи списков литературы одним отрезком

- Pack хранит единицы BIB_ENTRY после всех остальных единиц (`TRAILING_KINDS`). Сканирование всех записей читает один
  непрерывный отрезок.
- Единицы страницы лежат не более чем в двух отрезках. Формат входит в id pack'а и в манифест. Pack прежнего формата
  (страницы подряд) новый образ читает.
- Новый код сервиса: `kind_rows`, `scan`.
- Замер на копии late-артефактов итогового снимка (рабочая станция, только чтение):
  - сборка — 60 с (205 457 единиц, 24,3 млн токенов, 6,22 ГБ);
  - сканирование 23 350 записей — p50 335 мс, p95 367 мс (4 потока BLAS);
  - оценка 100 страниц-кандидатов — 14,6 мс с CP-42 и 18,7 мс по всем единицам.
- top-10 сканирования совпал с каналом стенда на 7 из 7 запросов. Пересечение top-100 — 99–100.
- Старый образ сервиса (`744ad09`) pack нового формата прочитать не может. Поэтому образ сервиса меняется раньше
  сборки pack'а, а задание обновления это проверяет (§9.6).

### 9.4 Q5: номер объекта усиливается только внутри темы

### 9.6 Обновление dense + late до снимка: задание и команды для CORE

Задание — `infra/core/lab_refresh.sh --snapshot <ID> [--wait-s N]`.
1. Проверяет, что `canonical/CURRENT` = `<ID>`. С `--wait-s` задание ждёт ограниченное время.
2. Проверяет, что `rx580-retrieval` работает на том образе, которым воркер соберёт pack (`VKM_RX580_IMAGE`).
3. Запускает `lab_stage2.sh`: dense только для новых и изменённых единиц, §64, новый k-NN-индекс, смена алиаса,
   smoke.
4. Запускает `lab_stage3.sh`: late только для новых и изменённых единиц, §64, pack, публикация, горячая замена,
   late smoke.

Итог DONE — только если обе стадии DONE на `<ID>` и совпадают три числа: единицы снимка, векторы dense-индекса и
единицы pack'а. Иначе итог INCOMPLETE или FAILED, код выхода ненулевой. Квитанция — `receipts/lab_refresh/<run>/`,
строка статуса — `receipts/lab_refresh/STATUS`.

Что уже известно:
- копии `lab_stage2.sh` и `lab_stage3.sh` на CORE совпадают с веткой (md5);
- `lab_stage2.json` на CORE ожидает jina-v5-nano;
- dense никогда не кодировал BIB_ENTRY, поэтому на новом снимке dense закодирует все его записи и новые группы
  блоков. Оценка по скорости этапа 2 (≈ 72 ед./с): для 24 488 таких единиц `…5d669f09` — около 6 мин;
- свободно 277 ГБ.

Обозначения:
- `<C>` — коммит слияния этой ветки, `<C12>` — его первые 12 знаков;
- `<ID>` — снимок после B3;
- `<compose>` — каталог compose на CORE, `<data>` — корень данных.

Команды выполняются из `<compose>`.

1. Проверки (только чтение):
   - `cat <data>/canonical/CURRENT` → `<ID>`;
   - `docker compose --profile jobs run --rm -T vkm-job search status` → `aliases.pages.built_from_snapshot_id` =
     `<ID>`.
2. Образы из дерева `<C>` (контекст — корень репозитория):
   - `docker build -f infra/core/api/Dockerfile -t vkm-corpus-api:0.1.0-<C12> .`
   - `docker build -f infra/core/rx580/Dockerfile.service -t vkm-rx580-retrieval:0.1.3-<C12> .`
3. Скопировать `infra/core/lab_refresh.sh` из `<C>` в `<compose>/`.
4. Сначала сервис RX580, потом pack:
   - сделать резервную копию `.env`;
   - в `.env`: `VKM_RX580_IMAGE=vkm-rx580-retrieval:0.1.3-<C12>`;
   - `docker compose up -d --no-deps rx580-retrieval`;
   - `docker compose exec -T rx580-retrieval curl -fsS http://127.0.0.1:8790/health` → dense и late резидентны,
     `late_store.status = READY` (старый pack `…86e7faa77770` читается).
5. API:
   - в `.env`: `VKM_API_IMAGE=vkm-corpus-api:0.1.0-<C12>`;
   - `docker compose up -d --no-deps api mcp mcp-admin`.
6. План задания: `bash <compose>/lab_refresh.sh --snapshot <ID> --dry-run`.
7. Запуск:
   - `systemd-run --user --unit vkm-lab-refresh --collect bash <compose>/lab_refresh.sh --snapshot <ID>`;
   - следить: `cat <data>/receipts/lab_refresh/STATUS` (и `lab_stage2/STATUS`, `lab_stage3/STATUS`),
     `journalctl --user -u vkm-lab-refresh -f`;
   - ожидаемый итог — `DONE snapshot=<ID> units_stage2=N units_stage3=N dense_index=N late_pack=N equal=True`.
8. Проверки после:
   - `docker compose --profile jobs run --rm -T vkm-job search smoke` — все проверки, среди них Q5;
   - маршрут: `docker compose exec -T api vkm-corpus search hybrid-smoke --api-url http://127.0.0.1:8000 --late --expect-route bibliographic --query "список литературы по ползучести каменной соли" --query "работы Баряха по сдвижению земной поверхности" --query "литература о закладке выработанного пространства"`
     → PASS; в выводе — `server_ms.bib_scan` (латентность сканирования на CORE) и `bib_route.units_scanned`;
   - обычные запросы не задеты: `… hybrid-smoke --api-url http://127.0.0.1:8000 --late --expect-route default` →
     PASS;
   - проба номеров рисунков V1 — с рабочей станции, только чтение, как в RESULTS_V1:
     `python benchmarks/retrieval_v1/scripts/figure_number_probe.py` с `J_V1`, `VKM_API_URL`,
     `VKM_API_TOKEN_FILE`.
9. Откат:
   - вернуть `.env` из копии и выполнить `up -d --no-deps rx580-retrieval api mcp mcp-admin`;

     старого формата старым образом воркера:
     `VKM_RX580_IMAGE=vkm-rx580-retrieval:0.1.2-744ad09dbb86 docker compose --profile jobs run --rm -T rx580-embed-worker pack --config /config/rx580.json --data-root /data --units /data/derived/embeddings/units/<ID>/vkm-units-v1-A --text-rule vkm-units-v1/A --publish --keep 3`.
