## 2. Классификация корпуса (все доступные источники, read-only)

### 2.1 Метод

Для каждой страницы PDF (PyMuPDF 1.28.2) считаются признаки:

- **Текстовый слой** (`get_texttrace`, без пробелов): кириллица, базовая латиница, Latin-1/extended (сигнал mojibake),
  греческий, цифры, пунктуация, управляющие символы, PUA, U+FFFD.
- **Доля невидимого текста**: render mode 3 или opacity 0.
- **Словоформы** и доля служебных слов RU/EN/DE/FR — мягкий сигнал правдоподобия.
- **Проверка ремонта**: если доля Latin-1 > 0,2, текст пробно перекодируется Latin-1 → CP1251, и повторно считаются доля
  кириллицы и служебных слов.
- **Шрифты**: Type0/Type3 без `/ToUnicode`, Type3.
- **Изображения** (`get_image_info()` **без** `xrefs`): число, покрытие страницы объединением bbox (сетка 64×64),
  наибольшее одиночное покрытие, эффективный DPI главного изображения, bpc, цветовое пространство.
- **Векторы**: число путей через `get_cdrawings()`.
- **Метки страниц** и сведения о документе: `is_repaired`, шифрование, метки, TOC.

Число страниц сверялось с pypdfium2 для всех PDF. DjVu разобраны как IFF-контейнеры: `FORM:DJVU` = страница, `DJVI` =
разделяемый словарь. Флаги DIRM декодированы. У каждой страницы определены INFO (размер, dpi) и наличие чанков
`Sjbz`, `BG44`, `TXTz`.

**Правило класса страницы** (пороги — параметры `classifier_version`, не константы кода):

| Класс | Условие (T — число непробельных глифов) |
|---|---|
| EMPTY | T < 20, нет изображений ≥ 5 % и путей < 500 |
| RASTER_SCAN (без текста) | T < 20, покрытие изображениями ≥ 0,5 |
| VECTOR, флаг VECTOR_NO_TEXT | T < 20, путей ≥ 500 (контурный текст, требует OCR) |
| MIXED, флаг IMAGE_NO_TEXT | T < 20, изображение ≥ 5 % |
| BROKEN_TEXT_LAYER (GARBAGE_GLYPHS) | (U+FFFD + управляющие)/T > 0,10 |
| BROKEN_TEXT_LAYER (MOJIBAKE_NOT_REPAIRABLE) | Latin-1/T > 0,30, и ремонт CP1251 не дал ≥ 50 % кириллицы и ≥ 5 % служебных слов |
| флаг REPAIRABLE_CP1251_REMAP | то же, но ремонт прошёл проверку правдоподобия; класс определяется дальше по общим правилам |
| BROKEN_TEXT_LAYER (PUA_GLYPHS) / флаг UNMAPPED_SYMBOL_GLYPHS | PUA/T > 0,10: если буквенная часть здорова — только флаг (формульные глифы), иначе BROKEN |
| RASTER_SCAN, флаг EMBEDDED_TEXT_LAYER | T ≥ 20 и покрытие ≥ 0,85; подфлаг HIDDEN_TEXT_LAYER (≥ 80 % текста невидимо) или TEXT_LAYER_VISIBLE_MODE (render mode ≠ 3, обычно текст под изображением) |
| MIXED | T ≥ 20, покрытие 0,15–0,85 |
| VECTOR | T ≥ 20, путей ≥ 500 |
| NATIVE_TEXT | остальное |

Низкая доля служебных слов **не** делает страницу битой — это только флаг LOW_FUNCTION_WORD_RATE. Все четыре
проверенных образца оказались нормальными: легенда таблицы или рисунка, график, листинг кода на Fortran, предметный
указатель. Первоначально немецкий текст 071 ложно попадал в BROKEN, пока в список служебных слов не добавили немецкие.

**Класс источника** считается по долям непустых страниц:

| Класс | Условие |
|---|---|
| NATIVE | ≥ 90 % NATIVE/VECTOR/MIXED |
| SCANNED_NO_TEXT | ≥ 90 % сканов без текста |
| SCANNED_WITH_TEXT_LAYER | ≥ 90 % сканов со слоем |
| SCANNED_PARTIAL_TEXT_LAYER | ≥ 90 % сканов, но разнородных |
| BROKEN_TEXT_LAYER | ≥ 50 % битых |
| MIXED | иначе |

**Последствия AGPL для PUBLIC.**

- В PUBLIC нет файла лицензии, значит, по умолчанию «все права защищены».
- AGPL-обязательства возникают при распространении комбинированной программы и при предоставлении изменённой
  программы по сети. Сервисы платформы работают только в LAN и только для владельца, поэтому практический риск низкий.
- Юридически это решение пользователя. Варианты:
  1. явно лицензировать код платформы совместимо с AGPL и перечислить PyMuPDF в зависимостях;
  2. держать PyMuPDF за адаптером `extract/backends/pymupdf_*.py` в отдельной optional-группе зависимостей и сохранить
     рабочий permissive-путь на pypdfium2.
- Рекомендация: вариант 2 технически. Интерфейс `PdfBackend` нужен в любом случае ради сверки и тестов.
- EbookLib — тоже AGPL-3.0+, поэтому не используется.
- SDK `glmocr` (Apache-2.0) тянет PyMuPDF как обязательную зависимость (§4.3) — ещё один довод не делать его основой
  pipeline.

### 3.3 EPUB (249)

- Разбор: `zipfile` + `lxml` (BSD). Путь: `META-INF/container.xml` → OPF → manifest и spine → XHTML.
- **Единица Page — spine-item** (391). Печатные номера берутся из якорей в порядке приоритета:
  1. `nav epub:type="page-list"`;
  2. NCX `pageList`;
  3. `epub:type="pagebreak"`;
  4. эвристика calibre `id="page_N"` (в 249 — 430 якорей).
  Каждый якорь хранит (spine-item, XPath или id элемента, смещение) и `printed_page_raw`.
- `bbox` у блоков EPUB нет. Локатор — `spine_idref` + id или XPath элемента + символьный диапазон; page space = UNKNOWN.
- Формулы 249, по признакам, — GIF без `alt` (881 файл, 753 якоря `EQN-*`). Каждая GIF становится Formula-кандидатом с артефактом-изображением и OCR «Formula
  Recognition:». MathML в 249 нет, но парсер его поддерживает.
- Записи литературы размечены id `BIBe-*` (229) — это нативная сегментация BibliographyEntry.
- Шрифты в `META-INF/encryption.xml` обфусцированы (4 TTF, A §2.6). На текст это не влияет, шрифты не нужны.

### 3.4 DOCX (023)

- `python-docx` (MIT) — абзацы (стиль, уровень заголовка, нумерация), таблицы (объединения ячеек), inline-изображения
  (rId → `word/media/*`).
- Сырой XML через `lxml`: OMML `m:oMath`/`m:oMathPara` (121/34) сохраняется как raw. Нормализованный LaTeX — конвертером
  OMML → LaTeX (pandoc в Phase 2: в Phase 1 023 читался через pandoc), со статусом конвертации.
- `lastRenderedPageBreak` (110) и явные разрывы (17) — это подсказки пагинации Word, а не страницы.
- **Производный PDF через LibreOffice нужен, но только как DERIVATION:**
  1. изображения страниц для визуального rerank и превью;
  2. совместимость с 538 записями evidence на страницах рендера LibreOffice 24.2.7.2 (A §2.6).

  Профиль рендера хранится в Page: версия LibreOffice, набор шрифтов, локаль, sha256 результата. Совпадение проверяет
  quote-check. Каноничны текст, таблицы и формулы из XML DOCX. Блоки привязываются к страницам рендера выравниванием
  текста — это DERIVATION с методом и оценкой.

### 4.3 План развёртывания (Phase 2, после одобрения; ничего из этого в Phase 0 не делалось)

1. **Модель.** Разовая загрузка `huggingface-cli download zai-org/GLM-OCR --revision 2e85a62… --local-dir <models>/zai-org__GLM-OCR/2e85a62`.
   Каталог — на ext4 внутри WSL или в томе Docker, не на DrvFs. Затем проверить sha256 `model.safetensors` против
   LFS-oid и записать receipt. То же для `PP-DocLayoutV3_safetensors@97d101e6…`.
2. **Compose** (`infra/workstation/glm-ocr/compose.yaml`; владельца каталога назначает координатор):
   - сервис `glm-ocr`, `image: vllm/vllm-openai@sha256:5f5e53…`, `gpus: all` или `deploy.resources.reservations.devices`;
   - том моделей только для чтения;
   - `ports: ["127.0.0.1:8080:8000"]`;
   - `ipc: host` или `shm_size`;
   - окружение `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `VLLM_NO_USAGE_STATS=1`, `DO_NOT_TRACK=1`;
   - сеть без выхода наружу там, где это возможно;
   - `.env.example` только с плейсхолдерами.
3. **Аргументы сервера** (стартовые, подбираются на canary):

   ```text
   vllm serve /models/zai-org__GLM-OCR/2e85a62 --served-model-name glm-ocr --dtype bfloat16
     --max-model-len 16384 --max-num-seqs 64 --max-num-batched-tokens 32768
     --gpu-memory-utilization 0.80 --limit-mm-per-prompt '{"image":1}'
     --speculative-config '{"method":"mtp","num_speculative_tokens":3}'
     --enable-prefix-caching --seed 0 --host 0.0.0.0 --port 8000
   ```

   - `max-model-len`. Полная страница A4 при 200 dpi (≈ 3,9 MP) — это ≈ 4,9 тыс. визуальных токенов: 19,7 тыс. патчей
     14×14, свёртка 2×2. Плюс до 8 тыс. токенов ответа. Итого 16 384. При 300 dpi для полной страницы нужно 24 576;
     регионы меньше.
   - KV-кэш — 64 KiB на токен (16 слоёв × 8 KV × 128 × 2 × bf16). При ≈ 8 GB свободной памяти это ≈ 120 тыс. токенов:
     64 регионных запроса по ≈ 2 тыс. или ≈ 16 полных страниц.
   - Prefix caching почти бесполезен: промпт короткий и идёт после изображения. Он оставлен как безвредное значение по
     умолчанию.
   - `gpu-memory-utilization 0.80` оставляет место для PP-DocLayoutV3 (0,5–1 GB) и рабочего стола.
4. **Endpoint.** OpenAI-совместимый `POST /v1/chat/completions`:

   ```json
   {"model": "glm-ocr",
    "messages": [{"role": "user", "content": [
      {"type": "image_url", "image_url": {"url": "data:image/png;base64,…"}},
      {"type": "text", "text": "Table Recognition:"}]}],
    "temperature": 0, "top_p": 0.00001, "top_k": 1, "max_tokens": 8192,
    "repetition_penalty": 1.1, "seed": 0}
   ```

   - Изображение — PNG без потерь, не JPEG, как в SDK.
   - Здоровье сервиса — `GET /health`, `GET /v1/models`.
   - Клиент разрешает только хосты `127.0.0.1`, `localhost` и имя сервиса compose. Тест это проверяет.
5. **Подача и скорость.**
   - Страницы идут конвейером: рендер (пул CPU 8–16 процессов) → layout (GPU, батч 4–8 страниц) → кропы → асинхронные
     запросы OCR (httpx, семафор 32–64 запроса «в полёте») → нормализация.
   - Порядок и повторы детерминированы (§7).
   - Grid на 50–100 страницах canary: `max-num-seqs` ∈ {32, 64, 128}, MTP k ∈ {1, 3, 5}, dpi ∈ {200, 300}, digest
     основной или cu134. Меряем стр./с, регионы/с, выходные токены/с, p50 и p95 задержки, утилизацию GPU (`nvidia-smi
     dmon`), VRAM, долю `finish_reason=length`.
   - Выбранная конфигурация фиксируется в receipt. Это настройка одного выбранного OCR, а не сравнение пяти движков.
6. **Оценка пропускной способности.**
   - Декодер маленький (0,5B), а MTP даёт ≈ 5 токенов за шаг. Основная цена страницы — визуальный энкодер: ≈ 0,4B × 20
     тыс. патчей на полную страницу 200 dpi, плюс квадратичное внимание. Разбиение страницы на регионы по layout
     уменьшает квадратичную часть.
   - На RTX 5070 Ti (≈ 0,45 от пропускной способности памяти A100 и заметно меньше тензорных FLOPS) реалистично
     **0,7–2 стр./с** для плотных книжных страниц при конкурентной подаче регионов. Разреженные страницы и мелкие
     формулы быстрее.
   - Пессимистичный план — 0,5 стр./с. Истину даст canary.
7. **Воспроизводимость.**
   - Digest образа, revision и sha весов, хеш аргументов сервера (`server_args_hash`), версии драйвера и рантайма
     пишутся в каждый сырой ответ и в receipt запуска.
   - Скрипт `smoke.py` проверяет text, table и formula на **синтетических** изображениях, сгенерированных тестом.
     Приёмка §55 — GPU/CUDA, скан, таблица, формула, сохранение сырого ответа, документированный старт.

Решение по SDK. Основой pipeline SDK не делать: MaaS по умолчанию, `abandon` меток, JPEG, переформатирование ответа, нет
сырых per-region запросов, PyMuPDF обязательной зависимостью. Использовать закреплённый SDK `v0.1.5` / `cef4d0ea` как
**эталон семантики**: промпты, классы layout, параметры генерации, склейка номера формулы. Свой тонкий клиент — около
300 строк. Если время поджимает, допустим SDK в режиме self-hosted при условиях:

- `maas.enabled: false`;
- `label_task_mapping` без `abandon`;
- `image_format: PNG`;
- сохраняется `json_result` страницы;
- явный флаг провенанса `SDK_FORMATTED_OUTPUT`.

## 5. Дизайн pipeline по стадиям

```
0 registry+sha → 1 container → 2 format detect → 3 page enumeration (expected N) → 4 page classification
→ 5 native extraction → 6 render → 7 layout → 8 OCR (где нужно) → 9 normalization → 10 Document Objects → (D: Parquet)
```

Каждая стадия пишет запись «page × stage»: статус, сигнатуру, ссылки на артефакты, ошибку (§7).

### 5.1 Стадия 0: реестр и SHA-256

- Реестр читается из `$VKM_RESOURCES_ROOT/00_registry/SOURCE_REGISTER.csv`, 251 строка.
- Для каждой строки: путь, существование, признак LFS-указателя (файл начинается с `version https://git-lfs`),
  `size_bytes`, потоковый SHA-256.
- Исходы:

  | Ситуация | Статус | Код ошибки |
  |---|---|---|
  | файла нет | UNSUPPORTED | `E_FILE_ABSENT` (retryable=false) |
  | LFS-указатель | FAILED | `E_LFS_POINTER` (retryable=true после `git lfs pull`) |
  | хеш не совпал | FAILED | `E_SHA_MISMATCH`, файл дальше не обрабатывается |

- Строка Source пишется всегда.

### 5.2 Стадии 1–3: контейнер, формат, перечисление страниц

**Формат определяется по магическим байтам, не по расширению:**

- `%PDF`, допускается мусор до 1024 байт — флаг `LEADING_BYTES_BEFORE_HEADER` (BOM у 020, 028, 050, 052, 064). Ремонт и
  производная копия для PyMuPDF и pdfium **не нужны**: оба открывают, число страниц совпадает. Нужен флаг и отказ от
  pdfminer. Здесь мы расходимся с A §2.7.
- `AT&TFORM` — DjVu.
- ZIP с `mimetype` = `application/epub+zip` — EPUB.
- `[Content_Types].xml` и `word/document.xml` — DOCX.
- Растровые изображения — PNG, JPEG, TIFF. Сейчас в корпусе их нет.

**Шифрование.** PDF открывается с пустым паролем. Метод и права записываются. У 239: RC4-128 (Standard V2 R3), запрещены
copy и print, разрешён accessibility. Флаг `PDF_PERMISSIONS_RESTRICTED` и решение политики (§11).

**Ожидаемое число страниц** — минимум двумя независимыми способами:

| Формат | Способы | Особенности |
|---|---|---|
| PDF | PyMuPDF и pdfium | совпало на 238 из 238 |
| DjVu | `djvused -e n` и собственный обход IFF с флагами DIRM | число страниц ≠ число файлов DIRM (053: 423 против 384) |
| EPUB | spine (linear и nonlinear) | метки страниц — отдельный список |
| DOCX | физических страниц нет | `app.xml Pages` — лишь подсказка; страницы — это страницы профиля рендера |

Расхождение способов → `NEEDS_REVIEW` / `E_PAGE_COUNT_MISMATCH`, никакого молчаливого выбора. Каждая страница 1..N сразу
получает строку со статусом `PLANNED` (только в операционном журнале).

### 5.3 Стадия 4: классификация и маршрут

Классификатор из §2.1 версионируется (`classifier_version`, пороги в конфиге). Маршрут страницы:

| Маршрут | Когда | Что происходит |
|---|---|---|
| `NATIVE` | NATIVE_TEXT, VECTOR с текстом, MIXED | текст нативный; OCR только для регионов §5.7 |
| `NATIVE_REPAIR` | REPAIRABLE_CP1251_REMAP | детерминированная перекодировка (DERIVATION); сырой слой сохраняется; проверка правдоподобия после ремонта; неудача → `OCR_REQUIRED` |
| `OCR_REQUIRED` | скан без текста, BROKEN, VECTOR_NO_TEXT, IMAGE_NO_TEXT, DjVu без слоя | OCR всех регионов |
| `OCR_OPTIONAL` | RASTER_SCAN со встроенным слоем, DjVu со слоем | встроенный слой становится `EMBEDDED_OCR_LAYER` с флагами качества; GLM-OCR — по политике сценария B; оба результата хранятся |
| `EMPTY` | пустая страница | проверка на «чернила» (§7.6) |

**Когда нативный текст хуже OCR** (решение по странице или региону, с `route_reason`):

1. Битый слой: U+FFFD, управляющие символы, PUA вне формул, нечинимый mojibake.
2. Встроенный чужой OCR-слой с низким правдоподобием (служебные слова, набор символов, систематические подмены) —
   переOCR, если выбран сценарий B.
3. Формулы. Нативные глифы формул линеаризованы, часто в PUA или Symbol. OCR региона даёт LaTeX, нативные глифы хранятся
   как raw-альтернатива.
4. Таблицы-сканы и таблицы без линеек, где `find_tables` не справился.
5. Контурный текст (025).
6. Подписи внутри растровых карт на нативных страницах — только опционально и с флагом.

**Когда нативное лучше OCR** — всегда для нативных спанов в текстовых регионах и для таблиц с линейками (точные цифры).
При расхождении нативного и OCR-вариантов хранятся оба, объект получает `NEEDS_REVIEW`.

### 5.4 Стадия 5: нативное извлечение (PyMuPDF, per page)

- **Текст.**
  - `get_text("dict"/"rawdict")` — блоки, строки, спаны: bbox, шрифт, размер, флаги, цвет, alpha, `char_flags`.
  - `get_text("words")`.
  - Плоский `get_text()` — совместим с хешами Phase 1.
  - Порядок чтения: хранить `native_order` (MuPDF) и `reading_order` (эвристика колонок и layout) с методом.
- **Шрифты.** `get_fonts`, `/ToUnicode`, Type3.
- **Изображения.** `get_image_info()` **без** `xrefs` и хешей: bbox, трансформ, px, bpc, цветовое пространство.
  Извлечение исходного потока (`extract_image`) — отдельная бюджетированная стадия для Figure.
- **Векторы.** `get_drawings()` сохраняется в gzip-JSON для страниц VECTOR и регионов рисунков; плюс SVG страницы или
  клипа (`get_svg_image(text_as_path=False)`) (§6.4).
- **Метаданные.** `doc.metadata`, XMP, TOC, метки страниц, ссылки, аннотации, встроенные файлы.
- **Таблицы.** `find_tables()` — кандидаты с ячейками (§6.2).
- **DjVu.** `print-txt` (зоны с координатами; y перевернуть), `print-meta`, `print-outline`. 037 — развороты 2-up:
  физическая страница остаётся единицей, делятся только кропы (§5.5).
- **EPUB и DOCX** — по §3.3 и §3.4.

### 5.5 Стадия 6: рендер

Профили версионируются: `render_profile_id` входит в `config_hash`.

| Профиль | Параметры | Назначение |
|---|---|---|
| `r200g` / `r200c` | 200 dpi, серый (сканы) или RGB, PNG | layout и полностраничный OCR (dpi по умолчанию в SDK) |
| `r300g` | 300 dpi, серый, PNG | кропы регионов сканов; для 600-dpi bitonal (052, 064, 238, 221…) — уменьшение до 300 dpi со сглаживанием; для 200-dpi JPEG-сканов (044) — брать исходное разрешение, не апсемплить |
| `prev1024` | длинная сторона 1024 px, WebP q80 (≈ 72–84 KB) или JPEG q85 | превью и визуальный rerank; размер согласовать с F под Jina m0 |
| DjVu | `ddjvu -scale=<dpi>` → PNG | 037: страница-разворот плюс кропы половин с флагом `SPREAD_2UP` |

- Детерминизм: закреплённые версии PyMuPDF и DjVuLibre; sha256 пикселей и файла; повторный рендер на canary. В Phase 0
  расхождений было 0.
- Хранятся превью всех страниц, OCR-входы OCR-страниц и кропы объектов. Рендеры layout нативных страниц не хранятся:
  они воспроизводимы, достаточно sha.
- **Page space.**
  - PDF: координаты `page.rect` после `/Rotate` и CropBox, в пунктах, начало слева сверху, y вниз. Хранятся `rotation`,
    `mediabox`, `cropbox` и матрица в user space PDF. Страниц с `/Rotate` — 26 (из них 12 у 045). Страниц крупнее A3
    нет: максимум ≈ 8,2 MP при 200 dpi.
  - DjVu: пиксели INFO × 72/dpi, начало слева сверху после переворота.
  - Рендер: `px = pt × dpi / 72`.
  - EPUB: page space = UNKNOWN.
  - Статус «page space» не географический.

### 5.6 Стадия 7: layout

- PP-DocLayoutV3, закреплённая revision, на `r200` **всех** страниц: нативных и сканов. Это единый генератор
  предложений регионов (figure, table, formula, text, title, header, footer, number, footnote, reference…).
  Цена — 10–25 минут GPU на корпус.
- Сырые детекции (класс, score, bbox, при наличии полигон) хранятся как артефакт JSON. Порог предложений — 0,3, как в SDK.
  Пороги создания объектов по классам — в конфиге, например 0,5 для figure, table, formula.
- Все классы сохраняются, `abandon` нет. `number` нужен для печатных номеров страниц, `footnote` — для ссылок,
  `reference` — для раздела литературы.
- Без GPU есть запасной путь для нативных страниц: рисунки из XObject-изображений и кластеров путей, подписи по шаблонам
  «Рис.», «Рисунок», «Fig.», «Таблица», «Table».

### 5.7 Стадия 8: OCR (только где требуется)

| Где | Что распознаём |
|---|---|
| `OCR_REQUIRED` | все регионы: text, table, formula; figure — `skip`, изображение сохраняется. Если layout ничего не нашёл на странице с «чернилами» — полностраничный `Text Recognition:` |
| `OCR_OPTIONAL` | по политике (сценарий B) |
| Нативные страницы | только регионы formula (→ LaTeX) и table, если `find_tables` не прошёл проверки (→ HTML) |

- Каждый запрос — кроп PNG → промпт по задаче → **сырой ответ целиком** (§7.1).
- `finish_reason = "length"` → `PARTIAL` / `E_OCR_TRUNCATED`. Повтор с большим `max_tokens` или с разбиением региона.
- Пустой ответ на регионе с чернилами → `NEEDS_REVIEW`.
- Повторяющиеся n-граммы (зацикливание) → флаг `REPETITION`.
- Несоответствие набора символов ожидаемому → флаг.

### 5.8 Стадия 9: нормализация

**Текст:**
- Unicode NFC.
- Обратимое снятие переносов: сырое хранится, операция — это флаг.
- Лигатуры и пробелы.
- CP1251-ремонт.
- Markdown → структура: заголовки, списки.

**Таблицы.** Сырой HTML → очищенный HTML (`table`, `tr`, `th`, `td`, `rowspan`, `colspan`) → сетка ячеек JSON (row, col,
rowspan, colspan, text) → CSV. CSV с потерями при объединённых ячейках — это флаг.

**Формулы.** Снять `$$` и `\[ \]`, нормализовать пробелы. Номер уравнения — по классу `formula_number` или regex вида
`(3.12)`. Семантики переменных нет: это правило v0.

**Печатные номера страниц:**
- `printed_page_raw` — строка;
- `printed_page_parsed` — int или римское → int;
- `printed_page_source` ∈ {PDF_PAGE_LABELS, RUNNING_HEADER_FOOTER_NATIVE, LAYOUT_NUMBER_OCR, EPUB_ANCHOR, DOCX_RENDER,
  NONE};
- `printed_page_status` ∈ {CONSISTENT_SEQUENCE, ISOLATED, CONFLICT, UNKNOWN}.

  Метки `/PageLabels` есть только у 62 из 238 PDF: в них 7 271 страница с меткой ≠ индексу и 162 римские метки. Остальным

### 6.1 Figure

**Поля:**
- `figure_id`, `source_id`, `page_id`;
- `bbox` (page space), `polygon` (опционально);
- `layout_class` (`image` / `chart` и др.), `layout_score`;

### 6.4 Векторные рисунки и страницы

Артефакт `vector_paths` — gzip-JSON вывода `get_drawings()`:
- items `l`, `c`, `re`, `qu` с точками в page space;
- fill и stroke, толщины, dash, even-odd, `closePath`, `seqno`, OCG-слой;
- для клипов — режим `extended`;
- матрица страницы.

Плюс `vector_svg` — SVG страницы или клипа региона. Растр **не заменяет** вектор. Для будущей CAD/GIS-конвертации
(агент G) это производный артефакт с провенансом (контракт §55). CRS-статус остаётся `PAGE_SPACE`: геопривязки нет,

### 6.5 BibliographyEntry (извлечение; связь с Work — контракт D)

**Поиск раздела.**
- Заголовок по регулярным выражениям над нативным или OCR-текстом:
  - RU: «Список литературы», «Литература», «Библиографический список», «Список использованных источников»;
  - EN: «References», «Bibliography»;
  - DE: «Literatur», «Literaturverzeichnis».
- Классы layout `reference` и `reference_content`.
- EPUB — `BIBe-*`.
- DOCX — стиль заголовка и нумерованный список.

**Сегментация.** Нумерация `^\d{1,3}[.)]` и `^\[\d{1,3}\]`, висячий отступ по bbox (x0 первой строки меньше x0
продолжения), интервалы. Для OCR-текста — по строкам.

**Разбор полей:**
- DOI: `10.\d{4,9}/…`;
- ISBN-10 и ISBN-13 с контрольной суммой;
- год 1800–2030;
- страницы (С., с., pp.), том и номер (Т., №, Vol., No.);
- авторы: «Фамилия И.О.», «И.О. Фамилия», «Surname, I.»;
- разделение «название // издание» (ГОСТ);
- `parse_confidence`.

Сырая строка записи хранится. Живёт в `$VKM_DATA_ROOT`, не в git.

**Связь с Work.** Извлечение выдаёт **кандидатов** с `match_method` ∈ {DOI_EXACT, ISBN_EXACT, TITLE_AUTHOR_YEAR_FUZZY,
CITATION_GRAPH_CROSSWALK (`CW-`/`WG-`)} и `match_score`. Работы автоматически не сливаются.

**Чужие страницы** («Горное эхо», A §2.8). Запись на странице с флагом `FOREIGN_PAGE` не приписывается Work хоста.

### 7.3 Idempotency и кэш

```
signature = sha256(canonical_json({stage, source_sha256, page_index, input_artifact_sha256*,
            pipeline_version, extractor_id, extractor_version, model_id, model_revision, config_hash}))
```

- `*` — хеши входов предыдущей стадии: рендер, сырой layout.
- `config_hash` покрывает только значимые для стадии параметры: профиль рендера, промпт, sampling, пороги layout,
  маппинг меток, версию классификатора.
- Версия бэкенда (vLLM, CUDA) пишется, но в сигнатуру **не** входит. Обновление движка не должно молча запускать
  переOCR: новый бэкенд проходит canary и включается осознанно. Опция `include_runtime_in_signature` — для строгих
  прогонов.

Запись «page × stage × signature» с терминальным статусом и существующим артефактом с верным sha — это кэш-попадание,
стадия пропускается. Состояние восстанавливается из канонических выходов и журнала в `$VKM_DATA_ROOT/ledger/`.
PostgreSQL на EDGE — лишь операционная копия: потеря PG корпус не теряет.

**CLI** (каталог `cli/` у координатора):

| Режим | Поведение |
|---|---|
| `--plan-only` | план (source, page, stage, причина: NEW, SIGNATURE_CHANGED, FAILED_RETRYABLE, FORCED) в JSON; ничего не исполняется |
| `--resume` | продолжить run, пропуская завершённые сигнатуры |
| `--force` | игнорировать кэш в заданной области: новые сырые файлы, старые остаются, новый `processing_run_id` |
| `--source VKM-SRC-044[,…]` и `--page 1-20` | выбор области; `--page` только вместе с `--source` |
| `--failed-only` | только FAILED с retryable=true; с `--include-nonretryable` — все FAILED |
| `--stage extract\|render\|layout\|ocr\|normalize` | выбор стадий |

### 7.4 Статусы

**Статус страницы** (канонический): `NATIVE_OK`, `OCR_REQUIRED` (запланировано, не выполнено), `OCR_OK`, `PARTIAL`
(часть регионов не удалась или обрезана), `UNSUPPORTED` (формат или политика, например retired ZIP или запрет прав),
`FAILED` (с ошибкой), `NEEDS_REVIEW` (сработали проверки качества или согласованности). `PLANNED` и `RUNNING` — только
в операционном журнале.

**Статус источника** — агрегат (`COMPLETE`, `PARTIAL`, `FAILED`, `UNSUPPORTED`) со счётчиками страниц по статусам.

### 7.6 Защита от silent page loss

Это инварианты. Их проверяет команда `verify` и unit-тесты; итоговую проверку делает агент I.

1. Строк Source 251, у каждой статус. Отсутствующий файл тоже получает строку.
2. Для каждого доступного источника ожидаемое число страниц совпало у двух методов, иначе `NEEDS_REVIEW`.
3. Строк Page ровно N, индексы 1..N без пропусков, `page_id` уникальны.
4. У каждой страницы ровно один терминальный статус на `pipeline_version`. После run не остаётся `PLANNED`.
5. Страница `OCR_REQUIRED` к концу run — `OCR_OK`, `PARTIAL` или `FAILED` с ошибкой. Никогда не `NATIVE_OK` с пустым
   текстом.
6. Страница с «чернилами» (доля не-белых пикселей рендера выше порога) и пустым итоговым текстом → `NEEDS_REVIEW`
   (`E_OCR_EMPTY_ON_INK`).
7. Сверка run: запланировано = выполнено + упало + взято из кэша + UNSUPPORTED.
8. Сверка с базой Phase 0:

   | Что | База |
   |---|---|
   | Страницы PDF | 23 105 |
   | Страницы DjVu | 2 870 |
   | Единицы EPUB | 391 |
   | Хеши текста Phase 1 | 2 447 (001–041); плюс quote-check по A §7 п. 20 |

   Расхождения — только с объяснением.

**Изоляция.** Каждый тяжёлый источник — отдельный subprocess с бюджетом времени и памяти:
- Linux: `RLIMIT_AS` или systemd-scope `MemoryMax`;
- Windows: job object;
- жёсткий пул воркеров.

При превышении бюджета — повтор в облегчённом режиме (оценка путей вместо `get_drawings`, без хешей изображений) с
флагом. Если и он не уложился — `FAILED` с `E_TIMEOUT`, но **строки страниц остаются**.

## 8. Предложение по ID (для D; решение за D, проверка — H)

- **Страница.** `page_id = VKM-SRC-NNN:pNNNN` — физический индекс с 1 для PDF и DjVu. Совпадает с `pdf_page` в evidence
  и с `pNNNN.txt` Phase 1; согласен с A §7 п. 12.
  - EPUB — `VKM-SRC-249:x0001`: spine-единица, другой вид, чтобы её не путали со страницей фиксированной вёрстки.
  - DOCX — `VKM-SRC-023:p0001` с `page_kind = DOCX_RENDER_PAGE` и `render_profile_id` в Page.
  - Поля Page: `page_kind` ∈ {PDF_PAGE, DJVU_PAGE, EPUB_SPINE_ITEM, DOCX_RENDER_PAGE} и печатные номера по §5.8.
  - Развороты 037 — физические страницы плюс `printed_pages_raw` из двух значений; отдельных page_id для половин нет.
- **Член архива** (если когда-то будет допущен) — `VKM-SRC-022!m0012`, страницы — `VKM-SRC-022!m0012:p0001`.
  Новых `VKM-SRC` не выдавать.
- **Объект на странице:** `{page_id}:{kind}{NN}` (kind: `b` блок, `f` рисунок, `t` таблица, `e` формула; NN —
  порядковый номер в reading order страницы), плюс **обязательные якорные поля**:
  - `generation` — версия семантики вывода для этого вида объектов, а не версия ПО;
  - `bbox_q` — bbox в page space, квантованный до 1/1000 ширины и высоты;
  - `kind`;
  - `content_sha256`.

  Пока `generation` не меняется, повторный запуск той же конфигурации даёт те же ID: детерминированный reading order
  плюс идемпотентность. Правки ПО без изменения сегментации меняют только `content_sha256` и `processing_run_id`
  строки. Смена `generation` даёт новые ID и таблицу `supersedes` (старый → новый, метод `IOU_KIND_TEXT`, порог IoU
  ≥ 0,9, score). Молчаливая перенумерация запрещена (A §7 п. 12).
  Альтернатива для D: хеш-ID `sha256(page_id|kind|generation|bbox_q)[:10]` устойчивее к вставке объекта, но хуже
  читается. Выбор за D.
- **Записи литературы** — уровень источника: `VKM-SRC-NNN:bib0001` в порядке раздела, с `page_id` начала записи.
- **Артефакты.**
  - `artifact_id = sha256:<hex>` — адресация по содержимому, дедупликация.
  - Путь человекочитаемый и детерминированный, без `:` (запрещён в Windows):
    `artifacts/<kind>/<source_id>/p0001.<profile>.<ext>` — например `page_renders/VKM-SRC-044/p0012.r300g.png`,
    `figures/VKM-SRC-014/p0105.f02.png`.
  - Сырой OCR — по §7.1.
- **Запуск.** `processing_run_id = run-<UTC YYYYMMDDTHHMMSSZ>-<8 hex>`, генерирует D или координатор.

Объём canary: ≈ 1 130 страниц плюс 391 единица EPUB. OCR: около 560 страниц и разворотов, 881 GIF, регионы формул и
таблиц 045, 014 и 197. Это десятки минут GPU.

Подробности R6, факты Phase 0:

1. `get_image_info(xrefs=True)` неявно считает хеши изображений, то есть декодирует их: **22 с на страницу** на 064
   (JBIG2 с общими глобалами). Без `xrefs` — 2–4 мс. Воркер первого прогона классификации завис на этом источнике.
2. `pdfminer.six` `get_page_labels()` — бесконечный генератор. Мой одноразовый пробный скрипт обернул его в `list()`,
   и за ≈ 5 минут процесс занял ≈ 150 GB commit при лимите системы ≈ 170 GB. Затем он сам завершился по MemoryError:
   исключение перехватил мой код. Убить процесс по PID мне не разрешили, и обходить этот запрет я не пытался.
3. FPDF вынес ресурсы в общий словарь: у каждой страницы числятся 238 изображений и 656 шрифтов.

Меры: бюджеты времени и памяти на воркер и страницу, изоляция в subprocess, запрет неограниченных итераторов, хеширование
изображений — только в отдельной стадии.
