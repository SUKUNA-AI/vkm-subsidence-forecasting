# AGENT K — RX580: резидентность и конкурентность (§4, §27–29, §49–50)

Дата: 28.09.2026. Директива пользователя: RX580 8 GB — держать dense и late-interaction модели резидентными
одновременно и обслуживать конкурентные запросы; reload — только если измерения докажут необходимость; без заранее
введённого глобального mutex/semaphore/single worker.

## 1. Методика

- Каждая модель — отдельный процесс `llama-server` (свой Vulkan-контекст, свои очереди команд); клиенты разных моделей
  не делят ни одной блокировки. RADV Polaris даёт 4 compute-очереди, ядро — 8 compute-колец: аппаратное перекрытие
  двух процессов возможно, и оно измеряется, а не предполагается.
- Харнес `vkm_corpus.embeddings.bench pair`: для пары (dense, late) —
  **MODE A** только dense, **MODE B** только late (каждая загружена одна, 2 клиента, запросы из пробы);
  **MODE C** обе резидентны, запросы по очереди (один клиент, dense/late чередуются);
  **MODE D** обе резидентны, 2 независимых клиента на модель, одновременно;
  **MODE D_bg** обе резидентны, 3 клиента на модель, у dense треть запросов — пакеты документов по 8 (фоновое
  кодирование корпуса во время интерактивных запросов);
  **MODE D_bg_sep** как D, плюс третий процесс `llama-server` того же dense-GGUF (2 слота), в который
  непрерывно шлёт один клиент пакетами по 8 документов (воркер эмбеддингов рядом с сервисом запросов).
  По 30 с на режим. Каждый режим: VRAM устройства (idle после прогрева / peak по сэмплеру 50 мс), VRAM и GTT каждого
  процесса (DRM fdinfo), p50/p95 латентности запроса по модели, запросы/с и документы/с, ошибки и OOM, число
  перезапусков (reload count), `gpu_busy_percent` (среднее, p95), RSS и CPU-секунды процессов, время движков GPU по
  процессам (`drm-engine-compute`/`gfx`).
- Латентность — клиентская: ids → HTTP → llama-server → JSON → постобработка (включая ColBERT-голову в шлюзе).
- GPU удерживается активным нагрузкой (runtime PM, см. BACKEND_RESEARCH §2.1); отдельно — латентность после простоя.

## 2. Общий backbone (§28) — факты по весам

| Семейство | Проверка | Результат | Решение для RX580 |
|---|---|---|---|
| BGE-M3 dense + sparse + multi-vector | одна модель | один проход (pooling none) даёт CLS (dense), `sparse_linear` и `colbert_linear` по скрытым состояниям | **одна резидентная модель**, три выхода; головы в шлюзе |
| jina-colbert-v2 (128) и -64 | сравнение safetensors | 294 тензора backbone совпадают побайтно, токенизатор тот же; голова 64 — своя матрица 64×1024 (не префикс 128) | **один GGUF**, головы 128/64 в шлюзе из одного прохода; 96 — Matryoshka-префикс 128 (вывод, не официальная модель) |
| pplx-embed-v1 dense и late | сравнение safetensors | 0 из 310 тензоров совпадают; отличия 0,8–2,3 % (отн.), словарь 151 936 против 151 671 | две модели; переиспользование весов невозможно без потери качества |
| mDenseOn и mLateOn | сравнение safetensors | 0 из 134 совпадают, отличия до 61 % | две модели |
| Qwen3-класс (Qwen3-Emb, jina-v5-small, pplx, Giga) | архитектура | одна архитектура llama.cpp, разные веса | общий бинарник и кеш шейдеров Mesa, но не веса |

Сложный shared-memory бэкенд (один процесс на несколько моделей) не нужен: VRAM двух моделей — сотни MiB из 8 GiB,
а раздельные процессы дают независимые очереди команд и изоляцию сбоев.

## 4. Вывод

- **TWO-MODEL RESIDENCY: PASS** для всех 7 пар: dense и late-interaction модели одновременно резидентны (буферы в VRAM,
  DRM fdinfo), обслуживают конкурентные запросы без глобальной блокировки, без ошибок, OOM и перезагрузок
  (reload count = 0). VRAM не ограничение: 286–412 MiB для пар малых энкодеров, 576 MiB с jina-colbert-v2,
  1,46–1,59 GiB для пар 0,6B-моделей и до 2,8 GiB с третьим процессом фонового кодирования — из 8 GiB.
- **Конкурентность реальна, но GPU один.** В MODE D суммарная пропускная способность пары выше, чем у любой модели в
  одиночку: granite-311m + mLateOn — 87 + 81 = 168 запросов/с против 100 (A) и 90 (B); granite-97m + mLateOn —
  163 + 81 = 244 против 170 и 90; jina-v5-nano + mLateOn — 103 + 70 = 173 против 111 и 90. Загрузка GPU 98–99 %,
  время движков двух процессов (≈ 27 + 28 GPU-с за 30 с) показывает перекрытие их ядер на разных compute-очередях.
  Латентность растёт с нагрузкой (p95 малых пар 14–30 мс в D против 13–26 мс в A/B; у пар 0,6B-моделей 85–96 мс) —
  вычислительный ресурс общий; это факт, а не повод для глобальной блокировки.
- **Фоновое кодирование корпуса — только отдельным процессом.** Если документы идут через тот же `llama-server`, что
  и запросы (D_bg), запросы ждут за пакетами документов: p95 dense 91 мс (granite-97m) … 1,3 с (causal Qwen3).
  Отдельный третий процесс того же GGUF (D_bg_sep) убирает очередь внутри сервера: у пары granite-97m + mLateOn
  фоновый воркер кодирует 128 док/с при p95 запросов 22 мс (dense) и 46 мс (late); у granite-311m + mLateOn —
  53 док/с при p95 42/43 мс; у 0,6B-моделей — 9–12 док/с при p95 133–183 мс. Рекомендация: воркер эмбеддингов на
  RX580 — отдельный процесс из очереди заданий; основное массовое кодирование — RTX после OCR (§34), RX580 —
  дополнительный воркер (для 0,6B-моделей — с паузой при интерактивной нагрузке).
- **Предпочтительная production-архитектура (§49):** обе модели финальной пары резидентны 24/7 как два процесса,
  keepalive 2 с, без reload. Выбор пары — по качеству (J); по RX580 лучшие по латентности пары — малые энкодеры
  (granite-97m/311m, jina-v5-nano) с mLateOn: в MODE D p95 14–27 мс (dense) и 27–30 мс (late) при 168–243
  запросах/с суммарно; пары 0,6B-моделей и пары с jina-colbert-v2 — p95 41–96 мс в MODE D.
- Повторные прогоны двух пар causal Qwen3 с `--cache-ram 0` (RSS dense-процесса 8,5 → 0,3 GiB) дали ту же
  латентность в пределах шума (D p95 89–96 мс против 67–102 мс): prompt cache расходовал память, но не время.
