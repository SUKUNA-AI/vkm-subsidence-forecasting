## 0. Итог

1. **Что сравниваем.** Шесть парадигм (§0): BM25, dense, learned sparse, late interaction, cross-encoder rerank и
   отдельный visual track. Всё сравнивается на одном наборе **единиц эмбеддинга** из канонических объектов (§3 этого
   документа), одним харнессом, с одинаковыми лимитами длины и официальными инструкциями каждой модели.
2. **Модели** зафиксированы точными ревизиями HF (коммиты), лицензии проверены (§8–9). 9 обязательных dense, 4 обязательные
   late-interaction конфигурации (jina-colbert-v2 в трёх размерностях — одна), 2 secondary с обоснованием, 2 visual.
   Qwen3-Embedding-4B исключена (§5 постановки). Все веса — 27,0 GB, загружаются в каталог моделей WORKSTATION с
   проверкой sha256 (receipt `MODELS_RECEIPT_RETRIEVAL.json`).
3. **Главный риск лицензий:** все модели Jina (v5-text, jina-colbert-v2, v5-omni, реранкеры v3.5/m0) — **CC BY-NC 4.0**:
   только некоммерческое использование, атрибуция, веса не распространяются. Для диплома и закрытой исследовательской
   платформы допустимо; при коммерциализации их нужно заменить или лицензировать. Остальные — Apache-2.0/MIT.
4. **Главный риск качества, известный заранее:** mDenseOn и mLateOn (LightOn) обучены на 9 языках **без русского**
   (карточка: en, fr, de, it, es, pt, sv, no, ar). Карточка mLateOn заявляет перенос на кириллицу; бенчмарк это проверит,
   исключать модели заранее нельзя (§47).
5. **Qrels** — graded 0–3, два уровня: **страница** (основной, стабилен при смене extraction generation) и **объект**
   (визуальный трек, формулы, таблицы). Основания: reviewed evidence vNext (локатор `pdf_page` → `page_id`), индекс
   объектов СКРУ-1, метаданные источников, явная проверка страницы; кандидаты без проверки в основные метрики не входят.
   После прогонов — pooling top-10 всех систем с добором оценок (§12).
6. **Разбиение** train/dev/test = 30/20/50 % по запросам, стратифицировано по категории, детерминированно (sha256);
   веса fusion, `k` RRF, глубины, инструкции-абляции подбираются только на train/dev.
7. **Пайплайны A–I** (§10) + два базовых (late как первый этап, BGE-M3 unified). Каждая ступень остаётся, только если
   даёт значимый выигрыш на test (парный рандомизационный тест + bootstrap CI, §14).
8. **GPU.** RTX 5070 Ti занят GLM-OCR. Решение координатора: референсные прогоны качества — на CPU в fp32
   (референсная точность); RTX — только в окне «очередь OCR пуста ≥ 5 мин и свободно ≥ 6 GB» (пауза после canary) или
   после полного OCR, с остановкой при появлении OCR-трафика и записью метрик OCR в начале и конце прогона (§15).

## 1. Принципы честного сравнения

- **Одинаковые единицы.** Все модели кодируют один и тот же список единиц с одинаковым текстом (правило
  `vkm-units-v1`, §3). Различается только то, что предписывает карточка модели (префикс/инструкция, пулинг).
- **Одинаковые лимиты длины.** Документная сторона: `max_doc_tokens = 512` токенов модели для всех single-vector и
  late-interaction моделей в основном прогоне (единица ≤ 1600 символов ≈ 350–450 токенов почти всегда целиком влезает);
  запрос — `max_query_tokens = 128`. Для ColBERT-моделей с обученной длиной запроса (jina-colbert-v2 и pplx-late — 32
  токена с расширением `[MASK]`) используется обученная длина — это часть модели, а не произвол; фиксируется в подписи.
  Длинные единицы (> 512 токенов) считаются и отчитываются (`truncated_units`); абляция `max_doc_tokens = 2048`
  отдельно.
- **Официальные инструкции.** Для instruction-aware моделей основной прогон — инструкция из карточки/конфигурации ST
  модели (таблица §7). Доменные инструкции — только абляция, подбор на train, проверка на dev.
- **Одинаковая нормализация и метрика близости.** Cosine для всех dense (L2-нормализация после пулинга), MaxSim по
  нормализованным токен-векторам для late, скалярное произведение весов для sparse. pplx-модели сравниваются в их
  нативном int8 (tanh-квантование — выход модели по карточке), float до квантования — диагностика.
- **Точный поиск в бенчмарке.** Кандидаты dense/late/sparse считаются полным перебором (единиц — тысячи): качество
  модели не смешивается с ошибками ANN. Влияние HNSW OpenSearch — отдельный инженерный замер (§13).
- **Никакой настройки на test.** Все подбираемые параметры — на train/dev (§11). Test оценивается один раз на
  замороженной конфигурации; каждое повторное обращение к test записывается в журнал прогонов.
- **Кеш без повторного inference.** Векторы кешируются по ключу (sha256 текста единицы, подпись конфигурации §37);
  одинаковый текст + одинаковая подпись → повторного вычисления нет (принцип §46).

## 2. Корпус бенчмарка V0

- Вход — **опубликованный снимок канона** (CANONICAL, `CURRENT` на CORE или его обратная копия на WORKSTATION, H-10).
  Решение координатора: **V0** = снимок после canary CP-23 (197, 044, 052, 045, 014, 037, 249, 023, 025, 064, 033, 042,
  005, 031, 202; с OCR) плюс, как только он будет опубликован, снимок нативного прохода полного прогона (все активные
  источники, страницы OCR_REQUIRED — без текста); **V1** — финальный снимок после полного OCR. Каждый прогон
  привязан к своему `snapshot_id`. В бенчмарк входят **все** объекты этих источников (как в production):
  остальной текст корпуса и есть естественные отрицательные примеры.
- Снимок пиннится: `snapshot_id`, `manifest_sha256`, число единиц по типам; всё это в receipt прогона. Смена снимка =
  новая версия бенчмарка (`retrieval_v0.<n>`), старые результаты не смешиваются.
- Оценка по источникам вне снимка невозможна: запросы, у которых после фильтрации по снимку не осталось ни одной
  проверенной релевантной страницы, исключаются из метрик и перечисляются в отчёте (`queries_without_judged_targets`).
- Оценка размера по данным dev-прогонов C (28.09): блоки TEXT — медиана 250–360 символов, p90 ≈ 700–800; EPUB 249 —
  7 134 блока на 389 spine-единиц. Canary + нативные источники дадут порядка 3–5 тыс. страниц и 8–15 тыс. единиц
  (оценка, уточняется по снимку).

## 3. Единицы эмбеддинга (§17), правило `vkm-units-v1`

Единица — не произвольный кусок в N токенов, а группа канонических объектов. Правило версионируется, как `page_text_v1`:
любое изменение поведения — новый идентификатор (`vkm-units-v2`).

Общее: только основной слой (`is_primary_layer = true`); текст — `normalized_text` канона (правило
`normalize_text_v1`); исключаются `PAGE_HEADER`, `PAGE_FOOTER`, `PAGE_NUMBER` (как в `page_text_v1`); единица не
пересекает границу страницы (страничные qrels отображаются точно; разрыв абзаца на границе страниц компенсирует
контекстный вариант C). `unit_id = "u1-" + sha256("vkm-units-v1|<тип>|<id объектов через |>|<часть>")[:16]`;
у единицы хранятся `object_ids`, `page_id`, `source_id`, `text_sha256`.

| Тип единицы | Состав | Лимиты |
|---|---|---|
| `BLOCK_GROUP` (semantic paragraph group) | подряд идущие блоки страницы в порядке `reading_order` типов TEXT, LIST_ITEM, ABSTRACT, TITLE, HEADING, FOOTNOTE, SIDE_TEXT, CODE, TABLE_OF_CONTENTS, OTHER, UNKNOWN; заголовок (HEADING/TITLE) открывает новую группу и прикрепляется к следующему тексту; CAPTION, на который не ссылается ни один рисунок/таблица (`caption_block_id`), и REFERENCE_LIST страницы без разобранных записей библиографии остаются в потоке, чтобы текст не терялся | цель 900 символов, максимум 1600; хвост < 200 символов приклеивается к предыдущей группе той же страницы; блок > 1600 символов режется по границам предложений на части (`part`) |
| `FIGURE` | `figure_label` + `caption_normalized`; + поясняющий текст: до двух блоков той же страницы, которые ссылаются на номер рисунка («рис. 3.1», «рисунок 3.1», «fig. 3.1»); если ссылок нет — ближайший предыдущий TEXT-блок | подпись без ограничения, контекст ≤ 600 символов; рисунок без подписи и контекста в текстовый трек не попадает (только визуальный) |
| `TABLE` | `table_label`, `caption_normalized`, `normalized_text` (линеаризованная таблица, строки через перевод строки, ячейки через ` \| `), + абзац-ссылка на таблицу | таблица ≤ 1500 символов (дальше — усечение с флагом), контекст ≤ 400 |
| `FORMULA` | `equation_label` + `normalized_latex` (иначе `raw_output`, если формат не IMAGE_ONLY), + предыдущий блок и следующий, если он начинается с «где»/«where»/«here» (экспликация переменных) | контекст ≤ 300 + 400 символов; формула без LaTeX/сырого текста в текстовый трек не попадает |
| `BIB_ENTRY` | `normalized_text` записи библиографии | как есть |
| `PAGE` (опционально, §17) | `pages.normalized_text` (`page_text_v1`) | первые 4000 символов; отдельная коллекция, не смешивается с остальными |

Основная коллекция поиска = `BLOCK_GROUP ∪ FIGURE ∪ TABLE ∪ FORMULA ∪ BIB_ENTRY`. Коллекция `PAGE` — отдельный
эксперимент «page-level vector против объектных единиц» (§17).

Отображение на страницы: ранжированный список единиц → ранжированный список различных `page_id` (первое вхождение).
Для страниц-дублей (кандидаты `duplicate_page_candidates`, копии одной Work — например, 025 ↔ 202) qrels ставятся
**обеим** страницам по содержанию, свёртка дублей — отдельная диагностика (`dup_collapse`).

Документы DOCX 023: объекты document-scoped, `page_id` — страница закреплённого рендера (RENDER_DEPENDENT). Рендер C
совпадает с Phase 1 до стр. 43 и расходится с 44-й (STATUS_C), поэтому qrels 023 со страниц ≥ 44 — кандидаты до сверки
текста по канону.

## 4. Контекстный эксперимент (§18)

| Вариант | Текст документа |
|---|---|
| A | только текст единицы |
| B | `«<название работы>. <раздел>»` + текст; название — `works.title` через `work_of_page`/`work_sources`; раздел — ближайший предыдущий HEADING/TITLE в порядке чтения источника (≤ 200 символов) |
| C | B + соседи: хвост предыдущей и начало следующей единицы той же страницы (по ≤ 300 символов, по границе предложения) |
| D | B + строка метаданных: `[авторы; год; издание; класс источника; область: <site_scope_raw>; с. <печатная метка>]` |
| CTX (только pplx-context) | late chunking по окну: единицы одного источника подряд в порядке чтения, ≤ 8 единиц и ≤ 4096 токенов на окно; каждая единица получает свой вектор с учётом окна; запрос кодируется той же моделью как документ из одного чанка |

Сравнение: pplx-embed-v1 на A/B/C/D против pplx-embed-context-v1 на CTX(A) и CTX(B); для остальных моделей B/C/D —
абляция на финалистах. Весь документ в каждую единицу не тащится (§18): окно CTX ограничено, варианты B–D добавляют
≤ 800 символов.

## 6. Late interaction (§8, §9)

- MaxSim: `score(q, d) = Σ_i max_j ⟨q_i, d_j⟩` по нормализованным токен-векторам; документные токены пунктуации
  отбрасываются там, где этого требует модель (skiplist pplx-late, `mask_punctuation` jina-colbert-v2).
- Два режима: (1) **late как реранкер** кандидатов fusion (top-100 → переупорядочивание); (2) **late как первый
  этап** — полный перебор MaxSim по коллекции (baseline «B-late»), чтобы измерить late-модель саму по себе.
- jina-colbert-v2 128/96/64: проверено — у `jina-colbert-v2-64` **тот же backbone** (294 тензора, максимум разницы 0),
  но **своя** 64-мерная проекционная голова, не равная первым 64 строкам головы 128 (макс. разница 0,15). Поэтому 64 —
  официальный чекпойнт; 96 — усечение 128-мерных токен-векторов с перенормализацией, помечено
  `NOT_OFFICIAL_96` (репозитория `jina-colbert-v2-96` на Hub нет, хотя карточка его называет); дополнительно усечение
  128 → 64 сравнивается с официальным 64. Общий backbone — готовый случай §28 (один проход encoder, две головы) для K.
- Хранение: токенов на единицу, `bytes_late = n_tokens × dim × bytes`, множитель к dense (`bytes_late / bytes_dense`),
  время MaxSim на top-100 и на полной коллекции — в инженерной таблице (§23).
- Решение по production ColBERT (§48): включается, только если выигрыш значим на test **и** стоимость хранения/латентности
  приемлема для RX580 (вместе с данными K).

## 11. Разбиение (§24, §59)

`splits.json`: для каждой категории запросы сортируются по `sha256("vkm-retrieval-v0|" + query_id)` и делятся
30/20/50 % (train/dev/test, округление в пользу test). Визуальный трек делится так же, отдельно. Правила:

- train — подбор весов weighted fusion, `k` RRF, глубин кандидатов, доменных инструкций (абляции);
- dev — выбор между подобранными конфигурациями и ранняя остановка абляций;
- test — только финальная оценка замороженных конфигураций; повторная оценка на test — с записью причины.

## 12. Qrels (§15)

Шкала: **3** central (страница прямо отвечает: содержит искомый факт, формулу, рисунок, таблицу); **2** strongly
relevant (существенное обсуждение темы, частичный ответ, тот же результат в другой форме/копии); **1** peripheral
(упоминание, контекст); **0** — явно проверено как нерелевантное (в том числе hard negatives).

Файл `benchmarks/retrieval_v0/qrels.tsv` (только ID и оценки, без текста):

| Колонка | Значения |
|---|---|
| `query_id` | ID запроса |
| `level` | `PAGE` (`VKM-SRC-NNN:pNNNN`, `…:rNNNN`, `…:sNNNN`) или `OBJECT` (`<page_id>:<f\|t\|m\|b\|c><12hex>`, `…:doc:…`) |
| `doc_id` | ID страницы или объекта (грамматика `vkm_corpus.ids`) |
| `grade` | 0–3 |
| `status` | `VERIFIED` (проверено явным просмотром страницы), `CANDIDATE` (предложено, не проверено), `NEEDS_REVIEW` (спорно) |
| `basis` | `EVIDENCE_VNEXT`, `SKRU1_OBJECT_INDEX`, `SOURCE_METADATA`, `PAGE_INSPECTION`, `POOL_JUDGMENT` (через `+`) |
| `evidence_ids` | ID записей evidence vNext через `;` (только ID) или пусто |

Процедура:

1. **Источники кандидатов.** (а) reviewed evidence vNext PRIVATE `11_evidence_vnext` — записи с `kind`, `pdf_page`,
   структурированными `data` (параметры, формулы, законы реологии, наблюдения, геометрия, библиография); `pdf_page` —
   физический индекс, `page_id = VKM-SRC-NNN:p<pdf_page:04d>` (CP-08); (б) индекс объектов СКРУ-1 (646 строк; тип
   объекта, `pdf p.N`, номер рисунка/таблицы) — для визуального трека и SKRU1-запросов; (в) метаданные источников
   (реестр, Work) — для bibliography/exact_entity; (г) поиск по тексту страниц.
2. **Проверка.** Каждая пара (запрос, страница) из кандидатов проверяется просмотром текста страницы (текстовый слой
   или OCR Phase 1 для 025/037; для сканов без текста — рендер страницы). Только после этого `VERIFIED` с оценкой.
   Предложения, сгенерированные моделью (включая самого J), — только `CANDIDATE` до проверки.
3. **Копии и дубли.** Для Work с несколькими копиями (013/025/202) релевантная страница одной копии ищется в другой по
   содержанию; обе получают оценку.
4. **Pooling.** После прогонов всех систем (dev и test) top-10 страниц каждой системы по каждому запросу, ещё не
   оценённые, проверяются по тем же правилам (`POOL_JUDGMENT`). Метрика покрытия — `judged@10` по системам; при
   `judged@10 < 0,9` у системы добор обязателен до финального отчёта.
5. **Спорные** — `NEEDS_REVIEW` с короткой причиной в журнале J (не в qrels). В основные метрики входят только
   `VERIFIED`; чувствительность: `NEEDS_REVIEW` как grade 1.
6. Для H (§60): журнал проверок (кто, когда, по какому основанию) — `work/…/retrieval_lab/judgments.jsonl`
   (git-ignored, PRIVATE-содержимое не публикуется), публичная часть — только колонки qrels.

## 14. Метрики (§22) и значимость

- Recall@10/20/50/100, MRR@10, nDCG@10/20 (линейный gain = grade, log2-дисконт, идеал — все проверенные оценки
  запроса), P@5/10. Бинарная релевантность — `grade ≥ 2` (строго), вариант `grade ≥ 1` — чувствительность.
- Уровень: страница (основной); объект — визуальный трек и запросы `formula_method`/таблицы; источник — диагностика.
- Срезы: `russian`, `ru_to_en`, `en_to_ru`, `vkm`, `skru1`, `physics`, `math`, `bibliography`, `long_context`, плюс
  по категориям.
- Значимость разницы систем: парный рандомизационный тест (10 000 перестановок знаков, фиксированный seed) и
  bootstrap 95 % CI для Δ nDCG@10 и Δ Recall@50 по запросам test. Ступень пайплайна «окупается», если Δ nDCG@10 ≥ 0,02
  и CI не содержит 0, а её стоимость (латентность, VRAM, хранение) приемлема по данным K.

| индекс | размерность, точность, байт на единицу, размер коллекции; HNSW OpenSearch: recall@100 против точного поиска |
| ColBERT | токен-dim, токенов на единицу (среднее, p95), векторов на документ, множитель хранения к dense, время MaxSim (top-100 и полный перебор) |
| RX580 | от K: backend, quant, p50/p95, VRAM, util, парность резидентности — берутся из отчётов K |

GPU-политика (CP-26), реализована в харнессе (`retrieval_lab.gpu`):

- RTX-окно (решение координатора): метрики vLLM (`vllm:num_requests_running` и `…_waiting`) равны 0 на всех опросах
  в течение ≥ 5 мин (опрос раз в 30 с) **и** свободная VRAM по `nvidia-smi` ≥ max(6 GB, потребность модели + 1 GiB);
  иначе — CPU (`retrieval_lab.gpu.idle_window`, `choose_device`);
- во время GPU-прогона проверка повторяется между батчами; появление запросов OCR — остановка и переход на CPU; метрики
  OCR в начале и в конце каждого RTX-прогона пишутся в `run.json`;
- контейнер GLM-OCR никогда не трогается; OOM сервера OCR недопустим (WDDM при переподписке выгружает память vLLM в
  системную — это тоже недопустимо, поэтому решает именно свободная VRAM, а не отсутствие OOM);
- CPU-прогоны — с `nice` и ограничением потоков (по умолчанию 8 из 28), чтобы не мешать pipeline C.

## 16. Пайплайны (§10) и трассировка (§54)

Глубины: каждый первый этап — top-100 единиц; fusion → top-100; late → переупорядочивание этих 100; реранк —
**top-24** (жёсткий лимит H-13 на вызов текстового реранкера, без склейки пачек; постановка §52 говорит «TOP 30», но
лимит gateway — 24). Текст для реранка — `rerank_text_v1` объектов единицы (для `BLOCK_GROUP` — конкатенация
`normalized_text` блоков, т. е. сам текст единицы; для рисунка/таблицы/формулы — правило объекта). Контракт F: весь
listwise-промпт v3.5 ≤ 4096 токенов, поэтому при 24 кандидатах каждый режется параметром `truncate_to_tokens = 150`
(число усечённых кандидатов пишется в трассу) — это production-ограничение, оно измеряется, а не обходится.

| ID | Состав |
|---|---|
| A | BM25 |
| B | dense (каждая модель) |
| B-late | late-interaction полным перебором (каждая late-модель) |
| C | BM25 + dense → fusion |
| D | BM25 + dense + sparse (BGE-M3 lexical) → fusion |
| E | C → late (MaxSim по top-100) |
| F | D → late |
| G | C → Jina reranker-v3.5 (top-24) |
| H | C → late → reranker-v3.5 |
| I | D → late → reranker-v3.5 |
| M3-unified | BGE-M3: dense + sparse + multi-vector одной моделью (взвешенная сумма, веса из статьи BGE-M3 как старт, подбор на train) — вход решения §50 |

Fusion: RRF (`k = 60` по умолчанию, подбор k ∈ {10, 30, 60, 100} на train) и weighted score fusion (нормализация
min-max или z-score по списку кандидатов, веса — сетка на train). Без реранкера (EDGE недоступен или не настроен
`VKM_RERANK_URL`) стадии G/H/I получают статус `NOT_RUN` — не «ноль».

Трассировка каждого запроса (`trace.jsonl` в каталоге прогона): для каждой единицы финального списка — ранги и скоры на
каждой стадии (`bm25`, `dense`, `sparse`, `fused`, `late`, `rerank`), ID страницы, время стадий.

BM25 — две реализации: (1) **OpenSearch** — экспериментальный индекс единиц `vkm-exp-<run>-units` с анализаторами E
(`vkm_text` + `.exact`, `vkm-analysis/1`), запрос E-стиля (multi_match best_fields + фразовый буст); индексы `vkm-exp-*`
удаляются после прогона; production-индексы E не трогаются; (2) **локальная** — BM25 (k1 = 1,2, b = 0,75, как Lucene)
с анализатором, повторяющим `vkm_text` (ё→е, стоп-слова ru/en, Snowball ru → Porter en, защищённые формы E); для
тестов и как контроль согласия с OpenSearch (Spearman рангов top-100 ≥ 0,9, иначе отчёт о расхождении).

## 17. Visual track (§11, §53)

- Коллекция: рендеры страниц и кропы рисунков/таблиц канона (`preview_artifact_id`, `image_artifact_id`,
  `render_artifact_id`); NOT_STORED_REPRODUCIBLE-рендеры воспроизводятся рецептом C.
- Путь: текст запроса → визуальный эмбеддинг запроса (V1/V2) → кандидаты по изображениям; параллельно лексика по
  подписям и тексту страницы (BM25) → fusion → top-8 → reranker-m0 (H-13: ≤ 8 изображений на вызов; F допускает 16,
  берётся минимум).
- Метрики — те же, уровень страница и рисунок; текстовый и визуальный треки не смешиваются (§11).
