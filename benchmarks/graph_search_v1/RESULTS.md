## 1. Решение

Основная метрика — `page_recall@50` на 78 test-темах topic_v1. У E она равна 0,317.

| Система | Выбрано на dev | Δ `page_recall@50` [95 % ДИ] | p | p (Холм) | Вред на retrieval_v1 | По умолчанию |
|---|---|---|---|---|---|---|
| G1 копии | — | +0,010 [+0,004; +0,019] | 0,002 | 0,011 | нет | нет: Δ < 0,02 |
| G2 связность раздела | вес 0,5 | +0,001 [−0,000; +0,004] | 0,50 | 1,00 | нет | нет |
| G3 синонимы и аббревиатуры | `post`, без узкого термина | −0,002 [−0,016; +0,014] | 0,85 | 1,00 | **есть**: R@50 текст (P) −0,022, p 0,015 | нет |
| G4 цитирования | `window` | −0,002 [−0,008; +0,004] | 0,63 | 1,00 | нет | нет |
| G5 темы | вес 0,5 | +0,010 [−0,002; +0,024] | 0,11 | 0,46 | нет | нет |
| **GC — все пять** | как выше | **+0,021 [+0,006; +0,037]** | 0,009 | **0,046** | нет (форма с группами копий) | **да** |

**По правилу §7 по умолчанию включается сочетание GC** — все пять стадий с параметрами, выбранными на dev. Ни одна
стадия по отдельности правило не проходит. В коде это `graph_stages.DEFAULTS`. Выключить без пересборки:
`VKM_HYBRID_GRAPH=none`. Включение на CORE — решение координатора.

**Что нужно знать о решении:**

1. **Запас мал.** Δ 0,0209 при пороге 0,02; p по Холму 0,046 при пороге 0,05.
2. **Выигрыш дают две стадии: G1 и G5.** Разведочно пара G1 + G5 без остальных даёт то же самое: +0,020
   [+0,007; +0,036] (§7).
3. **G3 одна вредит поиску retrieval_v1.** R@50 текстовых запросов (P) падает на 0,022 (p 0,015). В GC этот вред
   перекрыт вкладом G1 и G5.
4. **G4 ничего не даёт, а стоит дороже всех.** Лишний поиск BM25 до поздней стадии и около 12 лишних целей для
   MaxSim (§6).
5. **Проверка вреда у GC проходит только в форме с группами копий.** Эта форма предрегистрирована для систем с G1
   (§6 предрегистрации). В обычной форме у GC nDCG@10 текст (P) −0,009 (p 0,013) и R@50 −0,043 (p 0,002). Причина —
   копии, которые убирает G1: обычная метрика засчитывает один и тот же текст дважды (§4).

**Рекомендация.**

- Включить GC, как велит правило.
- Если координатор хочет осторожнее: `VKM_HYBRID_GRAPH=collapse,topics` (G1 + G5). Это разведочный вывод,
  подтверждения он не прошёл.
- Следующий шаг — подтвердить G1 + G5 отдельной предрегистрацией, например на пул-метках агента LB.

## 6. Задержка

**Измерено кодом сервиса на WORKSTATION:**

- функции стадий без поисков: у GC p50 0,49 мс, p90 0,64 мс; у каждой стадии отдельно ≤ 0,34 мс;
- `expand_query` (поиск синонимов G3 в NAV): p50 2,8 мс (с узким термином — 20 мс, выбран вариант без него);
- справочник стадий: 0,44 с один раз на сборку NAV. API строит его в фоне при старте.

**Не измерено на CORE — оценка.**

- **G3.** Поиск BM25 идёт в отдельном потоке с начала запроса, параллельно кодированию и первой стадии (в V1 они
  вместе ≈ 67 мс). Критический путь не удлиняется.
- **G4 в режиме `window`.** Один поиск OpenSearch с фильтром по источникам до поздней стадии: в V1 BM25 страниц стоил
  27–40 мс p50. Ещё около 12 целей MaxSim к 100 (поздняя стадия 65 мс p50 на 100 целей).
- **Итог для GC** — около 35–50 мс p50 сверху, в пределах цели 80 мс. Почти всё — G4.
- **Лабораторные числа — не CORE.** BM25 с маской источников в лаборатории стоит 70 мс p50: это numpy по 182 тыс.
  единиц.

## 7. Разведочные анализы (после чтения результатов; в решение не входят)

1. **Откуда выигрыш G1 на topic_v1.**
   - Если в выдаче E просто показать копии у каждой страницы, ничего не убирая: R@50 +0,014 (p < 0,001).
   - G1 против такой выдачи: −0,003 (0,27).
   - Итог: выигрыш G1 на topic_v1 почти весь в том, что цель находится через свою копию (метрика topic_v1 считает
     копии одной страницей). Освободившиеся места новых целей почти не добавляют.
2. **G1 + G5 без остальных стадий:** R@50 +0,020 [+0,007; +0,036], p 0,005 без поправки.
   - Проверки вреда (группы копий): nDCG@10 текст +0,025, R@50 текст **+0,012** (p 0,035), nDCG@10 визуальный +0,011.
   - В первых 10 только 2 неразмеченные страницы.
   - Выигрыш как у GC, но без потери R@50 от G3 и без задержки G4.
3. **GC по трекам topic_v1:**
   - процессы (48 тем) +0,023 (p 0,017); здесь работает G1 (+0,014);
   - семейства моделей (30 тем) +0,017 (0,28); здесь работает G5 (+0,023, незначимо).
4. **Механизм вреда G3.** Во всех 144 текстовых запросах из первых 50 ушло 90 релевантных страниц, пришла 41,
   изменились 48 запросов. Ветвь BM25 другой формулировки после поздней стадии поднимает лексические совпадения выше
   страниц, которые оценила поздняя стадия.

## Решение координатора (29.09.2026)

По умолчанию графовые стадии **выключены** (`graph_stages.DEFAULTS` пуст; `VKM_HYBRID_GRAPH` включает их без
пересборки). Основания:

- правило предрегистрации сформулировано по стадиям, и ни одна стадия отдельно его не проходит;
- комбинация GC проходит на грани (Δ 0,021 при пороге 0,02, p Холма 0,046), а в обычной форме nDCG теряет
  текстовые nDCG@10 −0,009 и R@50 −0,043 на retrieval_v1;
- G3 отдельно значимо снижает текстовый R@50 (−0,022);
- прирост G1 в основном — зачёт найденной копии, а не новые страницы.

Следующий шаг — подтверждающий предрегистрированный прогон G1 + G5 (апостериорно +0,020) на расширенной разметке
тем агента LB. Если он пройдёт, G1 + G5 станут умолчанием.
