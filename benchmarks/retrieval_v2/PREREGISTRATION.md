## 0. Вопрос

Плотная модель сервиса RX580 — jina-embeddings-v5-text-nano-retrieval: решение пользователя CP-39 по V0 (на canary
nano и Qwen3-0.6B были неразличимы, nano кодирует ≈ в 5 раз быстрее на RX580). Теперь корпус кодируется на RTX 5070 Ti
WORKSTATION за минуты, а RX580 кодирует только запросы. Вопросы V2:

1. Есть ли плотная модель, которая на полном корпусе значимо лучше nano внутри схемы сервиса E?
2. Добавляют ли эмбеддинги изображений страниц (визуальный канал) качество к E на визуальных запросах?

Правило §6 даёт **рекомендацию**. Решение о замене принимает пользователь.

## 3. Системы

Для текстовой модели m:

- **B:m** — только dense: точный косинус по 186 116 единицам, страница = её лучшая единица, без схлопывания дублей
  (как `B|dense` V1).
- **E:m** — схема сервиса E с m в dense-канале: RRF (k = 60) BM25 OpenSearch top-100 страниц и dense top-100 страниц
  m (группы дублей схлопнуты, как в сервисе) → late re-score mLateOn top-100 (оценка страницы = max MaxSim по её
  не-BIB единицам финального снимка) → top-100. Функции V1 (`page_ranking`, `rrf_pages`, `late_rescore`,
  `page_scores`) импортируются без изменений.
- **E** (база) — `E|rrf-prod>late@100` V1 (nano, Q8_0 RX580 — документы и запросы), пересчитанная кодом V2 из входов V1.
- **E:nano-gpu** — контроль: развёрнутая модель, закодированная в том же контуре, что и кандидаты.

Для визуальной модели v:

- **VIS:v** — только визуальный канал: точный косинус по 26 092 векторам страниц, без схлопывания дублей.
- **E+VIS:v** — RRF (k = 60) top-100 E и top-100 VIS:v (дубли схлопнуты) — основной вариант слияния.
- **E3:v** — RRF (k = 60) трёх каналов первой стадии (BM25, dense nano, VIS:v) → late re-score top-100 — вторичный вариант.

## 4. Метки и пул (`LLM_AGENT_V2`)

- **P1 (обязательно и полностью):** top-10 каждой E:m (оба трека), E+VIS:v (оба трека) и VIS:v (визуальный трек).
- **P2:** top-10 B:m (оба трека), VIS:v (текстовый трек) и E3:v (оба трека). Если новых страниц в P1 ∪ P2 больше
  5 000, P2 размечается до глубины 5, а системы P2 на P помечаются PARTIAL_POOL: показываются с judged@10 и ни в одном
  сравнении на P не участвуют.
- Протокол V1: оценка 0–3 по тексту лучших единиц страницы (лучшая по late-оценке и единица, которая её нашла, + подписи
  рисунков страницы), однострочное обоснование своими словами, источник `LLM_AGENT_V2`, статус CANDIDATE, основание
  POOL_JUDGMENT. Отличие от V1: пакеты **слепые** — без имён систем и рангов, кандидаты запроса упорядочены по
  page_id. Оценщик — агент V2 (LLM), как в V1; метки остаются CANDIDATE до ревью H.
- Для каждой системы на V и на P показывается доля неоценённых страниц в top-10 (1 − judged@10).

## 5. Метрики и статистика

- Основная метрика — nDCG@10 на уровне страниц, релевантно — оценка ≥ 2, линейный gain (модуль метрик V1).
  Вторичные — R@50, MRR@10, визуальный трек, срезы.
- Парный рандомизационный тест со сменой знаков (10 000 перестановок, seed 20260928), бутстреп-ДИ 95%.
- **F1** = {E:m vs E} для 10 кандидатов, текстовый трек, V, nDCG@10: поправка Холма по 10 (незапущенный кандидат
  входит с p = 1). **F2** = {E+VIS:v vs E}, визуальный трек, V, nDCG@10: Холм по 2.
- Проверка 0 (до всех оценок): пересчитанная E воспроизводит V1 — per-query nDCG@10, R@50, MRR@10 равны
  `results_v1.json` на всех 186 запросах на V и P. Не воспроизвелась — оценка не начинается.

## 6. Правило решения (рекомендация пользователю)

**Замена dense-модели.** m рекомендуется вместо nano, только если одновременно:

1. V, текстовый трек: Δ nDCG@10 (E:m − E) > 0 и p по Холму (F1) < 0,05;
2. P, текстовый трек: Δ nDCG@10 ≥ 0;
3. визуальный трек: ни на V, ни на P нет Δ < 0 с нескорректированным p < 0,05;
4. обслуживание выполнимо (§7).

Если проходят несколько — наибольшая Δ на P (текст); при разнице ≤ 0,005 — дешевле обслуживание (VRAM и
латентность RX580), затем разрешительная лицензия. Если не проходит никто — результат отрицательный или нейтральный,
nano остаётся. Справочно, без влияния на правило: флаг V1 «полезно» (Δ ≥ 0,02 и нижняя граница ДИ > 0), лицензия,
контроль E:nano-gpu.

**Визуальный канал.** VIS:v рекомендуется добавить как слияние E+VIS:v, только если:

1. V, визуальный трек: Δ nDCG@10 (E+VIS:v − E) > 0 и p по Холму (F2) < 0,05;
2. P, визуальный трек: Δ ≥ 0;
3. обслуживание выполнимо (§7).

Для всех запросов — если ещё Δ на P текстового трека ≥ 0 и на V текстового трека нет Δ < 0 с p < 0,05; иначе только
как отдельный маршрут поиска рисунков и страниц.

## 7. Выполнимость обслуживания

Проверяется для каждой модели, прошедшей пункты 1–3, и справочно — для лучших кандидатов.

- Кодирование запроса на CORE (RX580, llama.cpp Vulkan, 8 GiB) или EDGE (GTX 1650, 4 GiB; сейчас свободно 186 MiB —
  не цель). Нужен GGUF с вердиктом PASS гейта K (или конвертация и тот же гейт).
- Паритет качества: E:m с векторами запросов Q8_0 (тот же GGUF, llama.cpp; CPU-бэкенд как заместитель Vulkan,
  паритет Vulkan ↔ эталон уже измерен K) против E:m с векторами запросов bf16 GPU: |Δ nDCG@10| ≤ 0,005 на V и на P
  (текст), средний косинус векторов запросов ≥ 0,999.
- Латентность и VRAM: p50/p95 кодирования запроса на RX580 и VRAM процесса — из матрицы K (Q8_0); сумма резидентных
  моделей RX580 ≤ 7 GiB.
- Цена перекодирования: измеренная скорость 5070 Ti × единицы CURRENT-снимка (205 457); векторы — в существующем
  формате dense-артефактов (`derived/embeddings/dense/<model>/<revision>/<config-hash>/part-*.parquet` + manifest).
- Визуальные модели: текстовая башня `omni-small` — по весам совпадает с jina-v5-text-small (309 из 310 тензоров
  побитно, у матрицы эмбеддингов различаются 4 строки служебных визуальных токенов); если векторы запросов совпадут,
  запросы обслуживает GGUF jina-v5-small. Для `qwen3-vl-2b` — конвертация текстовой башни в GGUF и тот же паритет.
