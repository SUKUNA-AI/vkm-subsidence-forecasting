# TOPIC_BENCHMARK_V1 — предрегистрация тематического бенчмарка «от А до Я»

Агент Q, 28.09.2026. Набор, метрики и системы зафиксированы **до первого прогона** (правило предрегистрации
`docs/governance/VALIDATION_POLICY_RU.md`, §1). Любое изменение — новая версия набора (`topic_v2`) с пометкой.
Машиночитаемая спецификация — [`metrics_spec_v1.json`](metrics_spec_v1.json), хеши — [`SHA256SUMS`](SHA256SUMS).

## 1. Что проверяется

Пользователь просит тему («механика закладки», «гипотезы начальных напряжений») и ждёт всё относящееся к ней из
корпуса. Бенчмарк проверяет, находят ли инструменты страницы, которые люди уже признали свидетельствами по этой теме.

## 2. Набор (`topic_set_v1.jsonl`)

| | Темы | Запросы | Цели (страницы) |
|---|---|---|---|
| процессы PC-01…PC-72 (`catalogues/physics`) | 72 | 216 | 438 |
| семейства моделей MM-* (`MATHEMATICAL_MODEL_REGISTRY.csv`) | 45 | 135 | 448 |
| всего | 117 | 351 | 886 (39 источников) |

- **Запросы темы:** название (у процесса — имя из каталога дословно, у семейства — русское название, составленное
  по группам реестра) и два пересказа ([`topic_queries_v1.tsv`](topic_queries_v1.tsv)). Пересказы написаны без текста
  корпуса.
- **Цели:**
  - у процесса — страницы его 491 evidence-связи;
  - у семейства — страницы локаторов `VKM-SRC-xxx p.N` его моделей.

  Одна цель — одна каноническая страница темы. Градация: 2 — связь KEY, 1 — SUPPORT или локатор реестра. Основные
  метрики бинарные.
- **Исключены** семейства PDE (учебные уравнения, локаторов в корпусе нет) и DER (выведены проектом, это не тема
  корпуса).
- **Истина неполная:** цели — выборка релевантных страниц, а не сплошная разметка. Поэтому считается только полнота,
  точность не считается.

## 3. Правило страниц: `pdf_page` → `page_id`

Проверено сопоставлением цитат PRIVATE с текстом канона (квитанция [`page_mapping_v1.json`](page_mapping_v1.json),
1 142 записи):

- **`pdf_page` = `canonical.pages.page_index`** (тождество) для PDF и DjVu, включая развороты 2-up: одна
  каноническая страница на один скан разворота (011, 037, 002). Цитата найдена на той же странице в 891 из 963
  проверяемых записей (92,5 %), ещё 35 закреплены на соседней странице, 37 — слабое совпадение.
  - Остальные 179 записей проверить текстом нельзя: формулы, числа, короткие цитаты.
- **Соседняя страница:** если цитата уверенно найдена на странице в пределах ±3 (совпадение ≥ 0,6 и на 0,2 выше, чем
  на исходной странице), эта страница добавляется допустимой альтернативой.
- **DOCX VKM-SRC-023:** разбивка на страницы зависит от рендера (`RENDER_DEPENDENT`, id страниц `…:r0001`). До ≈ с. 44
  страницы совпадают с Phase 1, дальше сдвиг +1…+2.
  - Цель — страница, на которой найдена цитата.
  - Если цитату не найти — страница со сдвигом ближайшей уверенно найденной записи; исходная страница остаётся
    альтернативой.
- **Дубликаты:** страницы одной группы дубликатов (`duplicate_page_candidates`) засчитываются как одна.

## 4. Системы

| Система | Вызов | Роль |
|---|---|---|
| `hybrid_late` | `POST /v1/search/hybrid`, limit 50, candidates 100, late = умолчание сервера | развёрнутый поиск MCP `search_hybrid` |
| `hybrid_nolate` | то же, `late: false` | гибрид без MaxSim |
| `bm25` | `POST /v1/search`, limit 50 | вспомогательная база |
| `nav` | `search_sections` (20) + `explore_concept` (20) + top-units 5 соседних понятий | только навигационный слой |
| `dossier` | маршрут `reconstruct_topic` (настраивается) | адаптер; запускает координатор после развёртывания |

Ранжирование `nav`:

- взвешенный RRF (k = 60) списков: разделы поиска (вес 1), единицы найденного понятия (вес 1), единицы каждого
  соседа (вес 0,5);
- страницы читаются в два прохода: сначала входные страницы узлов, затем остаток каждого раздела.

## 5. Метрики

- **Страницы:**
  - `page_recall@10/@20/@50` — доля найденных целей в первых k страницах;
  - `mrr@50` — обратный ранг первой найденной цели;
  - `source_recall@10` — доля источников-целей среди источников первых 10 страниц.
- **Разделы** (`section_hit@10`) — цель лежит внутри одного из 10 верхних разделов:
  - у страничных систем это самые глубокие разделы NAV их первых 10 страниц;
  - рядом всегда показывается бюджет чтения `section_pages@10`.
- **Вспомогательные:** `capped_recall@k`, `success@10`, `section_recall@10`.
- **Агрегация:**
  - среднее по запросам;
  - разрезы: трек, группа процессов (14), вариант запроса.
- **Проверки:**
  - основные метрики `page_recall@20` и `mrr@50`;
  - пары `hybrid_late` против `hybrid_nolate`, `nav` и `bm25`;
  - парный рандомизационный тест по средним тем (n = 10 000, seed 20260928), bootstrap-ДИ 95 %, поправка Холма
    на 6 тестов.

## 7. Анализ промахов

- **Промах** — цель не найдена в первых 50 страницах ни одним из трёх запросов темы. Эталон — `hybrid_late`,
  `nav` разбирается отдельно.
- **Причины** (первая подходящая по порядку):
  1. `NO_TEXT` — нет текста;
  2. `VISUAL_EVIDENCE` — свидетельство с рисунка или таблицы;
  3. `LANGUAGE` — язык;
  4. `OCR_QUALITY` — флаги качества текста;
  5. `TERMINOLOGY` — слова запросов на странице почти не встречаются;
  6. `SECTION_MISSING` — только для `nav`;
  7. `DILUTION` — источник найден, страница — нет;
  8. `OTHER`.
- **10 худших запросов** — только ID.

## 8. Прогон

- Сборщик работает внутри контейнера API на CORE (`scripts/run_core.sh` → `docker exec -i vkm-core-api-1`).
- Вызовы API только на чтение, по одному.
- Токен читается из смонтированного файла и нигде не печатается.
- Сырые ответы содержат только ID и хранятся локально на хосте. В PUBLIC попадают только метрики и ID.
